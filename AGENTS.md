# Project: docx-validate

OOXML validators and redline/comment helpers for `.docx` and `.pptx` files.

- Repo: `jandira-tech/docx-validate`
- npm: `docx-validate` (unscoped)
- Language: TypeScript, ESM only
- Runtime: Node + Bun
- Build: `vite-plus`
- Tests: `vitest`
- Package manager: `pnpm`

## Code conventions

- File names: kebab-case (`merge-runs.ts`).
- ES modules only; no CommonJS.
- Relative imports between siblings; no path aliases.
- XSD validation: `libxml2-wasm` (via the `XsdValidator` interface in `src/lib/xsd-validator.ts`; the native `libxmljs2` addon was dropped — it ships no Node 26/ABI-147 prebuild and no longer compiles against Node's V8 headers).
- DOM work: `@xmldom/xmldom` + `xpath`, always via `src/lib/xml-helpers.ts`. Do NOT call `DOMParser` directly.
- Temp dirs: `tmp` via `withTempDir(async (dir) => { ... })` (`src/lib/run-cli.ts`). Don't ad-hoc `os.tmpdir()` + `mkdtempSync`.
- CLIs: `commander`, wired via `runCli(...)`.
- Validation results: return the `ValidationResult` shape from `src/lib/types.ts`. No per-validator shapes.
- Tests: one vitest file per module, fixtures under `tests/fixtures/` (`broken/` synthetic single-defect specimens, `working/` valid/repaired, `eigen/` real-world Plate/SuperDoc specimens, `external/` vendored third-party). Name fixtures `<subject>.<comment-or-error>.docx`; `scripts/apply-fixture-names.ts` derives names from content and `scripts/update-manifest.ts` regenerates `tests/fixtures-all.manifest.json` (which the `fixtures-all-{strict,lenient}` suites pin). `fixtures-all-word-valid.test.ts` instead pins validity against each attributable DOCX fixture's hash-bound Word observation; unknown, timeout, and stale observations are excluded, with floors of 358 clean opens and 67 rejections. The 24 jubarte lane specimens have separate integration coverage under `tests/lane/`.

## Schemas — golden source of truth

`src/scripts/office/schemas/` holds the official OOXML XSD schemas. Reference these whenever implementing or validating XML elements.

- `ISO-IEC29500-4_2016/wml.xsd` — WordprocessingML
- `ISO-IEC29500-4_2016/dml-main.xsd` — DrawingML
- `ISO-IEC29500-4_2016/shared-math.xsd` — Math
- `ecma/fourth-edition/opc-*.xsd` — Open Packaging Conventions
- `mce/mc.xsd` — Markup Compatibility Extensions
- `microsoft/wml-*.xsd`, `microsoft/word12.xsd` — Microsoft extensions

`defaultSchemasDir()` resolves to that directory.

## Behavioural notes

These are intentional behaviours of the implementation, documented at the call sites and verified by the vitest specs.

1. **Validator results are structured, not printed.** `validate_*` methods return `ValidationResult { valid, issues[] }`. The CLI shim in `validate.ts` is the only place that emits human-readable output. Tests assert on issue codes/messages.

2. **`@xmldom/xmldom` text-node mutation requires `.data`, not `.nodeValue`.** Validators that rewrite text nodes (whitespace repair, template-tag stripping) must use `(textNode as Text).data = …`. Writes to `.nodeValue` are silently dropped at serialization. See `validators/base.ts` near `_preprocessXmlForXsd`.

3. **`unpack`/`pack` byte parity is best-effort.** JSZip emits ZIP entries deflated with its own compression settings, so byte-for-byte round-trips against external tools are not guaranteed. XML pretty-printing/indentation is preserved so contents round-trip identically; the outer ZIP envelope can differ. This affects file-checksum equality, not logical-equivalence checks. Every XML part keeps the encoding it is stored in (#866): `unpack`, `pack`, `mergeRuns`, `simplifyRedlines`, `addComment` and the validators' auto-repair writers read part bytes through `decodeXmlPart` (`src/lib/xml-helpers.ts`; the file I/O is `src/lib/xml-part-io.ts`), which reports the encoding the byte order mark names, or else the declaration, and write the part back in it. A UTF-16 part stays UTF-16 in its own byte order, with its byte order mark if it had one, and an `encoding` pseudo-attribute a writer writes or rewrites in the declaration names the bytes: `UTF-16` beside a mark, `UTF-16LE` or `UTF-16BE` without one (#878); a declaration with no `encoding` pseudo-attribute keeps none, as XML then reads the encoding from the mark, or UTF-8 when there is none (#888); a UTF-8 part is written without a byte order mark, as before. A part whose declaration names an encoding this package cannot decode is left byte-for-byte untouched, and `addComment` returns an error naming it, changing nothing in the tree. The auto-repair writers neither count nor report a repair for such a part: `writeXmlPart` returns whether it wrote (#880), and a part's repairs are counted, and its verbose `Repaired:` lines printed, only after a write. The three repairs that rename one value in several parts — `repairCommentThreading`, `repairParaId` and `repairDurableId`'s hex rewrite — leave every part they would write untouched when one cannot be decoded (#889) or written (#909), and a write that fails or is refused after that check stops the repair, which counts only the parts already written (#920); no other repair renames a value across parts (#911). `repairDurableId` gives each over-cap `w16cid:durableId` one new value and writes it into every `w16cex:durableId` that named the old one, so `commentsExtensible.xml` stays paired with `commentsIds.xml` (#892). It matches the two parts' spellings as `xsd:hexBinary` values, so `ffffffff` in one and `FFFFFFFF` in the other get the same new value (#904). The decimal durableIds in `numbering.xml`, which no part references, keep their per-element renumbering, which runs whether the hex rewrite is refused by the check or stopped by a failed write; a failed write of a `numbering.xml` carrying only decimal durableIds does not stop the hex rewrite — before, one between two hex parts split the rename (#925); one that also carries a durableId the hex rewrite renames stops it, as any hex part's does (#942).

4. **`IGNORED_VALIDATION_ERRORS` contains only `"hyphenationZone"`.** `opc-coreProperties.xsd` imports the Dublin Core schemas from the bundled `schemas/dublincore/` copies (`dc.xsd`, `dcterms.xsd`, `dcmitype.xsd` — see `schemas/SOURCES.md`), so the former suppressions for the missing remote import (`"purl.org/dc/terms"`, `"dublincore.org"`, and the libxmljs2-era `"Invalid XSD schema"`) were removed. Schema-load failures surface as error-severity `xsd-schema-load-failed` issues — never silently valid and never message-suppressed. The remaining `"hyphenationZone"` entry is inherited from the Python validator with no recorded reason; full lenient validation still applies it. Strict never suppresses schema findings through the list, and full DOCX/DOCM Word-valid runs no XSD, so it does not consult the list or emit `xsd-strict-skipped`.

5. **`compareParagraphCounts` returns a structured result.** `{ original, modified, delta, originalUsesStrictNamespace }`. With `verbose: true`, also prints `Paragraphs: N → M (+K)` to stdout before returning.

6. **XML diagnostics retain available source positions.** `checkXmlSyntax` parses original bytes without recovery and emits `xml-syntax`, `xml-undeclared-prefix`, or `xml-encoding` with the part path and available 1-based line/column. DOM decoding supports UTF-8 and UTF-16 via BOM/declaration. Strict schema findings retain available engine lines; when preprocessing changes the XML, the message identifies lines in the transformed validation view. Lenient keeps its capped, deduplicated XSD message path. External entities are not loaded or expanded, and XSD resources resolve through allowed local roots.

7. **`accept-changes.ts` wraps `runSoffice()` in `runSofficeWithTimeout(args, 30000)`.** Node's `child_process.spawn` has no built-in timeout that resolves cleanly with stdout/stderr, so the wrapper is a `setTimeout`-driven Promise.

8. **`validateWhitespacePreservation` uses `[ \t\n\r]`, not `\s`.** JavaScript's `\s` is broader (matches `\f`, `\v`, Unicode whitespace), so the explicit character class is used to keep the match set predictable.

9. **`RedliningValidator` class wraps free functions.** `RedliningValidator.validate()` and `.repair()` delegate to the free-function implementation. `repair()` returns `0`.

10. **Full `.xlsx` validation returns a silent structured error.** `runValidators` returns `code: "unsupported-file-type"` without writing to stderr; the CLI renders it. Other unrecognized suffixes fail target dispatch before this point. Partial selection can still run registered package/XML checks on XLSX.

11. **`repairWhitespacePreservation` prints a per-repair line when `verbose: true`.** `Repaired: <file>: Added xml:space='preserve' to <tag>: <preview>` per element fixed.

12. **Namespace constants exported from `validators/docx.ts`:** `WORD_2006_NAMESPACE`, `WORD_STRICT_NAMESPACE`, and `WORD_PARAGRAPH_NAMESPACES` (a `readonly [string, string]` tuple).

13. **`validateNamespaces` walks all descendants for `xmlns:*` collection.** This mirrors lxml's `nsmap` propagation: namespace prefixes declared on child elements (not just the root) are collected.

14. **`pack()` accepts an `inferAuthorFunc` callback.** `inferAuthorFunc?: (unpackedDir: string, originalDocx: string) => Promise<string> | string`. When omitted, the default `inferAuthor` from `simplify-redlines.ts` is used.

15. **`validate()` exposes `xsdWalk` and optional `metadata`.** DOCX/DOCM default to `word-valid`; PPTX keeps `lenient` and its existing XSD validator, which walks the schemas under every profile, `word-valid` included, so a PPTX can report `schemaCompleted: true` under any profile (#340). For DOCX/DOCM, Word-valid document validation runs no XSD: `xsdWalk` is `{ started: false, parts: [], eligible: 0 }` and `metadata.schemaCompleted` is always false. Full lenient and strict runs walk eligible parts (lenient can return before XSD on malformed XML). `metadata` reports `profile`, the registry ids the run executed in `executedChecks` (#319), selection omissions in `omittedChecks`, `schemaCompleted`, and optional `wordVerification`. The byte APIs forward mode and verifier options and return metadata on the shared `ValidationResult`. Each schema walk keeps its own trace and engine-failure count, and the walk that finishes last leaves its own on the validator, so a walk nested in another on the same validator no longer lists parts twice or loses the outer walk's engine failures (#943).

16. **Packaged CLI: `dist/cli.mjs` is the only live shim in the bundle.** `src/cli.ts` is the `docx-validate` bin (package.json `bin`), a second `pack.entry` that calls `runCli(import.meta.url, ...)`. The per-script `runCli` shims stay in `src/scripts/**` for `tsx` execution, but `vp pack`'s `inertCliShimsPlugin` rewrites their metaUrl to a never-matching `file:` URL — bundled modules share one `import.meta.url`, so a shim without the rewrite would fire on `node dist/index.mjs` and import (#314). New CLI entry points belong in `pack.entry` + `bin`, never as `runCli` calls the barrel can reach.

17. **Named Word rules run through the registry and scheduler.** `src/scripts/office/checks/index.ts` registers `WORD_RULE_CHECKS` for full `word-valid` and `strict` DOCX runs; lenient keeps the other validators. Check definitions declare `requires` and registration order puts prerequisites first. `xml-syntax` gates by part: malformed parts are hidden from dependent DOM rules while well-formed parts are still judged. It and the validators' XML passes (`BaseSchemaValidator.xmlFiles`) judge the parts `xmlPartNames` in `checks/xml.ts` returns: an `.xml`/`.rels` name, or any name `[Content_Types].xml` declares with an `application/xml`, `text/xml` or `application/…+xml` type, so a main document stored as `word/document.bin` is judged as its `.xml` twin (#620, session 32). Prerequisites run once; a failed gate with no part-scoped errors skips its dependents. `runChecks()` exposes per-check outcomes, including `unavailable` for archive-only checks on directories; top-level metadata is not that status trace.

18. **CLI and API selectors share `mode-policy.ts`.** `--strict` / `strict: true` selects the strict profile. `--quick` / `quick: true` selects `QUICK_CHECK_GROUPS` (`package`, `xml`, `content-types`, `relationships`, `tables`, `drawings`). `--checks` / `checks` selects registered ids or groups plus prerequisites, without the full validator's other methods. A partial run selecting a check that reports its own parse failures also runs `xml-syntax` as a companion without gating that check, and suppresses restated parse findings for rejected parts (#385); under lenient it stops where `xml-syntax` fails, as the full lenient run stops at a malformed part (#391). A partial run applies its profile as a full run does, so it never fails a package the full run passes (#381). Under lenient it runs neither the Word rules nor the ZIP-envelope checks: naming one, or only groups made of them, is a `ModeConflictError`. Under word-valid it reports a DOCX check's error that Word tolerates as a warning, through the `isWordBlockingIssue` predicate in `validators/word-blocking.ts` that the full run uses. Strict rejects partial selection and conflicting profiles; quick and named selection are mutually exclusive. A partial run never repairs, so `--auto-repair` / `autoRepair: true` with `--quick` or `--checks` is refused rather than ignored (#652). API conflicts throw `ModeConflictError`. `--list-checks` and `--help` need no package or engine startup. Full CLI runs that walk schemas (`profileWalksSchemas(format, profile)`: DOCX/DOCM under lenient and strict, PPTX under every profile) compile a small XSD startup probe outside the document `xsdWalk`; Word-valid DOCX/DOCM, XLSX, and partial runs bypass it (#318, #341). Partial runs compile no XSD, list omitted check ids, name what has no id in an `Also not run:` line (the format validator's own rules, where a full run walks schemas the schema walk, and for a DOCX given `--original` the redlining validation, #353), and print `Selected checks passed`, never `All validations PASSED!`, even when no registered check was omitted (#339); `--json` renders `{ valid, issues, metadata }` for completed runs. See README for the complete named-check catalogue and advisory rules.

19. **Real-Word verification is optional and separate from portable success.** `--verify-word` / `verifyWord: true` uses `src/lib/word-verifier.ts` (or an injected `wordVerifier` callback). The built-in transport needs macOS, installed Microsoft Word, and host-terminal Accessibility automation permission. It opens an exact-byte temporary copy, requires the matching document to stay dialog-free for 3 seconds, and uses a default 45-second launch/observation/cleanup budget with up to 2 seconds reserved for close. Only `clean-open` satisfies verification; `repair-warning`, `open-error`, `crash`, `password-prompt`, `unknown-dialog`, `timeout`, and `unavailable` do not. Metadata records the hash, platform, wall-clock timestamp (`wallNow`, never the deadline clock; #329), elapsed observation, details, and available Word version/build. Requested-but-unsatisfied verification makes `valid` false even without error issues. Directories have no packed bytes and are unavailable. `crash` requires a Microsoft Word crash report written after this run's open; a vanished Word without one (an external kill or quit) is `unavailable` (#305). The version and availability calls race the same budget (#320). A verifier that throws yields `unavailable` instead of rejecting `validate` (#333). A dialog already showing before open makes the run unavailable without opening or closing anything (#315). Verification needs exclusive use of Word: runs must not overlap and Word must not be in use, because a dialog that appears after the pre-open observation is attributed to this file (#331). macOS close dismisses the Word dialog showing at close (Cancel, No, OK), which under exclusive use is the one this run's open raised, lets an open that overran its budget settle before closing (#328), closes only its copy without saving, and never quits or force-kills Word or relaunches it after a crash.

20. **Manifest Word evidence is hash-bound.** `src/lib/word-provenance.ts` reads `word: { outcome, sha256, observedAt?, wordVersion? }`; a hash mismatch is `unknown`. Legacy strings remain readable but have no hash to check. Unknown, timeout, crash and stale observations, and unmapped outcome spellings, do not count toward clean/rejected accuracy; only `open-error`, `unreadable-content-warning`, `password-required` and `unknown-dialog` are rejections, and `toManifestOutcome` maps verifier outcomes to these spellings (#316). `mergeWordObservation` retires superseded observations into `history` and preserves attributable same-byte evidence against timeout/unknown re-probes. `test:fixtures:refresh` uses the provenance-preserving `scripts/update-manifest.ts`; review expectation changes individually rather than treating current validator output as Word evidence.

21. **The file-reference walk skips External targets under word-valid and strict.** `validateFileReferences` in `validators/base.ts` does not resolve a `TargetMode="External"` relationship's target as a part (ECMA-376 Part 2 §9.3), so `file:///…`, UNC and `ftp://` targets draw no `rels-broken`; Word 16.115 opened External `.rels`, `/_rels/` and `../customXml/` targets clean, direct and in a selected Choice (session 40). Lenient keeps its historical scan, which skips only `http…` and `mailto:` (#665). Word-valid and strict skip only the `http:`, `https:` and `mailto:` schemes, so a relative target that merely starts with `http` resolves as a part: Word refused `httpimage1.png/.` beside the stored `word/httpimage1.png` and opened the plain `httpimage1.png` clean (session 79, s79a, two runs, all readings agree), and word-valid had accepted the folder target (#988). Any other scheme (`ftp:`, `httpfoo:`) makes the target an absolute URI that names no part, which they report as `rels-broken` ("it spells a URI scheme, which names no part"); it blocks word-valid in a story root's sidecar for the `styles` type and for a `header` the source part references, where Word offered recovery beside the well-formed `word/ftp:…` part the path spells (session 87, s87c/s87d, two runs, all readings agree), and keeps a warning for every unprobed placement: an unused header, the package relationships part and every other type (#1127). They read the scheme ASCII case-insensitively (RFC 3986 §3.1), so an `HTTP:` or `MAILTO:` target is skipped as its lowercase spelling is, where it was resolved as a part; lenient's scan stays case-sensitive, and Word has been shown neither spelling as an internal target (#1008). Under every profile, both file-reference walks (`rels-broken` in `validateFileReferences`, `rels-target-missing` in `validators/docx.ts`) read an internal target naming a folder as broken: a final `.` or `..` segment, a trailing `/`, or a target reaching the package root (`relationshipTargetFolder` in `src/lib/content-types.ts`), where the file-system join they use dropped the final `/` and found the stored part the path spells. Its `rels-broken` registers the folder with its final `/` (the root as `/`), and blocks word-valid whatever the relationship type: Word offered recovery for every such target it was shown beside that stored part — `officeDocument`, `footnotes`, `customXml`, `styles`, `settings`, a used and an unused `header`, an unused `image` and the core properties — and opened each plain target clean (sessions 70 to 73, two runs each, all readings agree; #975). That block, and #734's for a broken target naming a relationships part or a `customXml` part outside `word/`, applies only in a relationships part Word reads to reach the stories: `_rels/.rels` and a story root's own sidecar, the main document's or a reached glossary's. Word opened clean a folder target in the sidecar of an unreferenced part (session 79), of a used header whose text it rendered, of an unused header and of the styles part (session 80), and an absent escaping `customXml` target in the sidecar of the unreferenced part and of the used header, two runs each, all readings agree, so there `rels-broken` warns (#987); the `customXml` shape in an unused header's or the styles part's sidecar is unprobed (#1006). An External target names no part, so lenient's historical scan keeps resolving it as before. Both walks stop a climb above the package root at the root (`packageTargetPath` in `validators/base.ts`, which resolves the dot segments as part-name segments before any file-system join, so a climb cannot come back into the tree through the unpacked directory's own name), as RFC 3986 and Word read it: a stored part there is the one the target names, so word-valid no longer rejects a stored root `customXml/item1.xml` named by `../../customXml/item1.xml` or `/../customXml/item1.xml`, which Word opened clean (session 76), and no profile calls the part unreferenced; Word also read an escaping styles and header target (session 75) and notes target (session 74) from the root. An absent stopped part stays broken under its name (session 54's block holds), and only a symbolic link still escapes (#984).

22. **`repairMissingParaIds` keeps the stamps ignorable.** On each part it stamps, it declares `w14` on the root and lists it in the root's `mc:Ignorable`, reusing the root's prefix for the compatibility namespace or declaring `mc`; a root binding `w14` or `mc` elsewhere is left alone. The repair count is unchanged (#653, session 40).

23. **`deadlineMs` bounds the whole `validate()` run, cooperatively.** `src/lib/run-deadline.ts` holds `RunDeadline`. `validate()` starts it at entry, and every step asks `reached(step)` before it starts: the package stages in `validate.ts`, each check in `runChecks` (`RunChecksOptions.deadline`), each rule the DOCX/PPTX validator schedules through `ruleScheduler()`, each part of `validateAgainstXsd` (the rest are counted in `xsdWalk.notExamined`), the redlining validation, and Word verification, which gets `timeoutMs`: the rest of the budget, at most 45 s. `ruleScheduler()` runs the DOCX rules one after another only when a deadline is set; without one they still all start at once. A step already running finishes, so a run overruns by at most its longest single step, and the profile's severity policy still applies to what ran. A stopped step makes the run invalid, with exactly one error-severity `validation-deadline` finding and `metadata.deadline: { budgetMs, notRun }`. The validators append their own copy (`withDeadlineFinding`); `validate()`'s `withDeadline` replaces it with the run's. `deadlineMs` with `autoRepair` is a `ModeConflictError`, and a budget that is not a finite number of 0 or more is a `RangeError` (the CLI exits 1) (#630).

24. **A refused item name no longer hides the rest of a packed package.** A stored name that places no part (a leading `/` or `\`, a drive, or an empty or dot-only segment; `entryNameRefusal` in `src/lib/validation-context.ts`) still refuses the staging with `package-extract-failed`, which names the first one. The stored-names-only check `opc-item-name-refused` (`checks/opc-item-name-refused.ts`) names each one, as an error under every profile, and Word-blocking: Word 16.115 rejects every kind, even for an unreferenced entry, with the recovery offer for a leading `/` or `\`, a drive, and an empty, `.`, `..` or `...` segment (#411; sessions 3, 42 and 43). The full run of a packed file then stages `archiveWithoutEntries(bytes, …)` (`src/lib/zip-central-names.ts`): the archive with the refused central-directory records dropped and the end record's counts and size rewritten, so an entry a refused `..` name hid in JSZip's name-keyed view is judged by its own bytes. It validates that subset through the same `runStaged(…)` path a clean packed package takes: the original archive's envelope and stored-name findings, reported once and never recomputed; the format validator's own rules and the schema walk; and the same extraction-failure fallback (`archiveFindings` on the subset bytes), deadline step and packed-repair disclosure. It then appends the original `package-extract-failed` and forces `valid: false`; `xsdWalk` and `metadata.schemaCompleted` describe the subset's walk (#629). When the subset's own extraction fails — the host folds two kept names `assertPlaceableNames` does not, as APFS folds `Å` and `å` — the run returns what it returned before #629: one `package-extract-failed`, naming the first refused name, beside `archiveFindings` on the subset bytes, and no repair disclosure (#874). A ZIP64 archive is rewritten too whenever `zip64Tail` can move its tail, as `centralKeyedArchive` moves it (#479): the record and locator follow the shrunk directory, with the record's entry counts and directory size and the locator's absolute record offset (#521) rewritten, and the 32-bit EOCD's fields only where they are not saturated. Nothing more is judged when the subset cannot be built (a ZIP64 tail `zip64Tail` refuses, or bytes between a non-ZIP64 directory and its end record), does not load, or its remaining names still collide (#413, #441). A partial run of a packed file keeps its design: its own part-reading selection (`archiveFindings`' `select`) on the same subset bytes, after the selected stored-name and envelope checks ran on the original archive, so its errors stay a subset of the full run's (#381). Directory inputs are unchanged: they report the stored-name findings and the extract failure (#629).

## ISO OOXML Strict XSD validation

ISO OOXML defines two conformance classes: **Transitional** (backward-compatible, widely used) and **Strict** (pure ISO, uses different namespace URIs under `purl.oclc.org/ooxml/` instead of `schemas.openxmlformats.org/…`). Example: Strict WML uses `http://purl.oclc.org/ooxml/wordprocessingml/main` vs Transitional's `http://schemas.openxmlformats.org/wordprocessingml/2006/main`.

The official ISO Strict schemas are bundled under `src/scripts/office/schemas/iso-strict/` (ECMA-376 Part 1, 5th edition — see `schemas/SOURCES.md` for provenance, sha256s, and the two local fixes needed to make them compile: the xml.xsd import and three `default="off"` → `default="false"` attribute defaults in wml.xsd).

**Current behaviour:** `validateAgainstXsd` in `validators/base.ts` detects Strict conformance by checking each XML file's root element `namespaceURI` against the `http://purl.oclc.org/ooxml/` prefix (`_isStrictXmlFile`). Under `profile: "strict"`, Strict parts dispatch to the matching iso-strict schema by part identity (`STRICT_SCHEMA_MAPPINGS`); OPC parts (content types, rels, core properties) share one namespace across both conformance classes and always use the OPC schemas, and Strict parts with no mapped schema are skipped like any unmapped part. The glossary document's parts (`word/glossary/*.xml`) map to the `word` key and the DrawingML diagram parts (`diagrams/{data,layout,quickStyle,colors}N.xml` below a main content folder) to `diagram` (`dml-diagram.xsd`, #628); `xsdWalk.parts` lists every part sent to the engine. Every other well-formed XML part the walk reaches draws one `info`-severity `xsd-no-schema` issue naming it, without changing validity, `xsdWalk` or `metadata.schemaCompleted`; a malformed part, a Strict part lenient skips and a part the deadline never reached draw none (#628). A direct `validateAgainstXsd()` call, outside a full run, has no recorded XML pass, so it parses an unmapped part with `checkXmlSyntax` before auditing it, and a malformed one draws none there either (#867). The PresentationML parts one folder below `ppt/` whose root pml.xsd declares map to the `ppt` key, matched by folder and file name, ASCII case-insensitively (`PPT_PART_NAME_BY_FOLDER`): `slides/slideN.xml`, `slideLayouts/slideLayoutN.xml`, `slideMasters/slideMasterN.xml`, `notesSlides/notesSlideN.xml`, `notesMasters/notesMasterN.xml`, `handoutMasters/handoutMasterN.xml`, the legacy `comments/commentN.xml` and `tags/tagN.xml` (#864). ## Known gaps

- **Of equivalent part names, only one entry is judged (#351).** `opc-equivalent-part-names` reports equivalent stored part names and multiple content-types stream spellings: an error under strict and under word-valid for DOCX/DOCM (Word 16.115 offers recovery for every duplicate spelling probed, `docs/plans/evidence/word-probes-2026-10-24.md`), a warning under lenient. The content of the dropped entries is not validated. The package view still prefers an exact normalized part-name match, otherwise the first OPC-equivalent entry in code-unit order; slash/backslash aliases keep the normalized spelling, otherwise the first stored spelling in code-unit order. The content-types stream keeps `[Content_Types].xml` when present, otherwise the first matching spelling in code-unit order. On a file system insensitive to case or Unicode normalization, full extraction still stops at `package-extract-failed` for collisions (#373, #376); the diagnosis runs on the archive's central-directory names, so two entries under the identical spelling are reported too — Word-blocking, since Word offers recovery for them as well — while the package view reads the last stored entry (#411).

- **soffice end-to-end tests are gated on `process.env.SOFFICE_AVAILABLE`.** Both `tests/accept-changes.test.ts` and `tests/soffice.test.ts` skip real-LibreOffice invocations unless that env var is set; CI images typically don't include LibreOffice. Run with `SOFFICE_AVAILABLE=1 pnpm test` locally to exercise them.

- **`eslint-plugin-functional` is dropped.** It loads typescript-eslint, whose `ts-api-utils` needs TypeScript's JS compiler API, and TypeScript 7 (Go-native) ships none: the plugin crashes oxlint at startup. Its one enabled rule, `prefer-property-signatures`, is replaced in the `src/**` override by oxlint's native `typescript/method-signature-style: property`. Its three type-aware rules (`immutable-data`, `no-mixed-types`, `prefer-readonly-type`) were already off, since oxlint's JS-plugin runtime gives plugins no parser services.

```bash
pnpm run check          # vite-plus check
pnpm run build          # produce dist/
```

Coverage-enabled Vitest runs, including failed runs, print `Coverage: N% lines, M% branches` and write text, JSON-summary, HTML, and LCOV reports. `scripts/coverage-gate.ts` reads `coverage/coverage-summary.json`: the listed new modules need 80% lines / 70% branches; mode policy, scheduler, registry, and result aggregation need 90% / 85%. A gate with no matching coverage fails. CI runs the gate after full coverage tests; a focused run is not a substitute.

The installed-package smoke is opt-in: `PACKAGE_SMOKE=1 pnpm exec vitest run tests/package-artifact.integration.test.ts --coverage`. It checks consumer imports/validation, bundled Transitional/ISO Strict/Dublin Core schema assets, one packaged CLI help usage, and a silent library entry. The separate real-Word lane is `WORD_VERIFY=1 pnpm exec vitest run tests/word-verifier.word.test.ts --coverage` on macOS with Word and host-terminal Accessibility permission; portable tests do not make fresh Word observations.

## Real-Word probes

- **Always check twice, with logs.** A Word observation goes into `tests/fixtures-all.manifest.json` or `docs/plans/evidence/` only after two separate Word runs of the same bytes. Each run's verdict is read from that run's Word log, not only from a parsed outcome table:
    - a repair prompt is the dialog `Word found unreadable content in <file>`;
    - an open error is the dialog `Word experienced an error trying to open the file … (<file>…)`;
    - a clean open is a converted PDF with no dialog naming the file.

    A verdict counts only when both runs and both logs agree. If they disagree, record `unknown` and report the disagreement. Never pick one run.

## Desired Conversion Methodology

**Desired Conversion Methodology** means fully parsing the original document into a semantic, format-independent representation — extracting its content and the meaning of that content (including its structure, formatting, and relationships, and every other discrete constituent component of the document (each, an "**Element**")), and not its byte form, such that the document can be faithfully reconstructed into any target format.

Where an Element cannot be parsed semantically by available means — including, by default, DrawingML (`<w:drawing>`), VML pictures (`<w:pict>`), and embedded OLE objects (`<w:object>`) (each, a "**Non-Parseable Element**") — the Desired Conversion Methodology nonetheless applies in full to the entire document and to every Element enclosing that Non-Parseable Element; only the single, irreducible Element that resists semantic parsing may be preserved verbatim, and only after custom parsing techniques have been exhausted to reduce that residue to the smallest possible extent.

For the avoidance of doubt, the Elements enumerated above are not the sole Non-Parseable Elements; every time an Element is classified as a Non-Parseable Element, such classification must (i) emit a warning during code execution (at runtime), and (ii) be documented in `AGENTS.md`, `README.md` and `CLAUDE.md`.
