## Violation 1 — `concatenated-duplicate-zip-archive` (ZIP envelope; 1 site)

**Offending bytes** (binary envelope, no XML; positions per the proven assessment):

```text
EOCD #1 @18741: PK\x05\x06 disk=0 cd_disk=0 entries=14/14 cd_size=896 cd_offset=17845 comment_len=0 → ends @18763
EOCD #2 @37504: PK\x05\x06 disk=0 cd_disk=0 entries=14/14 cd_size=896 cd_offset=17845 comment_len=0 → ends @37526 (EOF)
bytes[0..18762] == bytes[18763..37525] — an entire second copy appended after the first EOCD
```

Note the mechanism: EOCD #2's `cd_offset=17845` points into the **first** copy's central directory
(the second copy's real CD sits at 18763+17845=36608), which is why backwards-scanning tolerant
readers still recover all 14 entries while Word's stricter reader refuses the file.

**Rule.** No bundled XSD governs the ZIP envelope — `src/scripts/office/schemas/` holds OOXML/XSD
part schemas only (`opc-*.xsd` cover content-types/relationships/core-properties XML). The governing
rule is PKWARE .ZIP File Format Specification APPNOTE.TXT §4.3.1 (fetched this ask to
`tmp/d9d3739d-verify/APPNOTE.TXT`, lines 336–341):

> 4.3.1 A ZIP file MUST contain an "end of central directory record". A ZIP file containing only an
> "end of central directory record" is considered an empty ZIP file. Files MAY be added or replaced
> within a ZIP file, or deleted. **A ZIP file MUST have only one "end of central directory
> record".** Other records defined in this specification MAY be used as needed to support storage
> requirements for individual ZIP files.

Two EOCDs in one file violate the bolded sentence. The offending site exists and abides by the
assessment's byte layout; I confirmed the identical layout on a reconstruction (below), but not on
the specimen's own bytes, which are absent.

**Proposed fix — repair the source document:** truncate the file to its first 18763 bytes
(`head -c 18763` / delete bytes 18763–EOF). That is the assessment's proven minimal change:
`unreadable-content-warning` → `clean-open`. Stripping the leading copy instead is equivalent — the
copies are byte-identical, so either prescription yields the same 18763-byte archive. Every part
byte is unchanged; only the duplicated envelope goes away.

**Fix target:** `repair` (broken source document; there is no producing redline tool to change).

## Where the fixes belong and why

- **repair** — the document's envelope is the defect, and the fix is the proven truncation above.
- **Not docx-validate.** The analyst's "validator misses it" claim does not reproduce. This branch
  registers three ZIP-envelope checks for full word-valid/strict DOCX runs
  (`src/scripts/office/checks/index.ts:146-148`), including `zip-bytes-before-archive`
  (`src/scripts/office/checks/package.ts:35-52`). On the concatenated shape, JSZip rebases onto the
  second copy — `readCentralDirectoryView` computes `zero = eocd - (cd_offset + cd_size)`, i.e.
  37504 − 18741 = 18763 (`src/lib/zip-central-directory.ts:299`) — so `zipBytesBeforeArchive`
  returns 18763 and the check fires an error. The sibling `zip-bytes-after-eocd` stays silent
  because the first copy's EOCD is skipped as a prefix record (#464;
  `src/scripts/office/zip-bytes-after-eocd.ts:129`), but the defect is caught either way: if the
  central-directory view were unreadable, `countZipBytesAfterEocd` would instead report the 18763
  bytes hidden behind the earlier record (`zip-bytes-after-eocd.ts:121-133`). The analyst's
  contrary "All validations PASSED!" run cannot be re-checked (file gone); it is contradicted by
  the shape test below and should be re-run on the restored specimen before anyone adds a new check.
