## Each violation

### 1. `zip-bytes-after-eocd` — 663 undeclared bytes after the end-of-central-directory record (severity: error)

**Site.** File offsets, from my own parse this session: EOCD signature `50 4B 05 06` at offset 23253; `.ZIP file comment length` field reads 0; the 22-byte record therefore ends at 23275. The file continues to 23938 — 663 bytes past the record, beginning:

```text

```

decoded (PHP server output, first lines):

```html

(output started at /www/jskonsorcium.cz/www/core/file.php:96) in
<b>/www/jskonsorcium.cz/www/core/control.php</b> on line <b>88</b><br />
<br />

(file/97/Technické parametre- Atypické žalúzie- ISSO retiazka.docx) in
/www/jskonsorcium.cz/www/core/control.php:89

```

The archive proper is internally consistent — `cd_offset 22484 + cd_size 769 = 23253` = the EOCD start, 12 entries — so the envelope is well-formed **except** for the trailing data. No package part holds this defect; it is container-level, which is why no bundled XSD under `src/scripts/office/schemas/` governs it.

**Rule.** PKWARE ZIP Application Note (APPNOTE.TXT), fetched this session:
- §4.3.16 field table: `end of central dir signature 4 bytes (0x06054b50)` … `.ZIP file comment length 2 bytes` / `.ZIP file comment (variable size)` — the only bytes permitted after the record are the comment the record's own length field declares.
- §4.3.1: "A ZIP file MUST contain an 'end of central directory record'." and "A ZIP file MUST have only one 'end of central directory record'." §4.3.6's overall-format diagram ends at `[end of central directory record]`.

With comment length 0, the file must end at offset 23275. Word offers to recover the document for bytes beyond it — the exact behaviour this repo's check encodes (`src/scripts/office/checks/package.ts:16-33`, counter at `src/scripts/office/zip-bytes-after-eocd.ts:152-180`, user-facing explanation at `src/scripts/office/validators/word-error-explanations.ts:129-130`).

**Proposed fix.** Truncate the file to its first 23,275 bytes — delete the 663 bytes after the EOCD record; do not touch any preceding byte, and do not re-zip (a repack would also work but is unnecessary and changes unrelated bytes). Optionally re-fetch a clean copy from the source service once it stops emitting PHP errors into the download stream.

**Fix target:** `repair` (broken source document).

## Where the fixes belong and why

- **repair (this issue's prescription).** The document's parts are fine; the defect is server-side output pollution. `docxcorp.us` proxies a conversion at `jskonsorcium.cz` whose `control.php` fatal error ("headers already sent", then "Command not found") was appended after the ZIP payload was already flushed. Deleting the trailing bytes is proven (assessment line 14) to make Word open the file clean, and I reproduced that locally: the truncated copy passes this repo's default profile with `All validations PASSED!`. Upstream, the source service must buffer or abort its output instead of concatenating error text onto a binary stream — that belongs to the service, not to any repo tool.
- **docx-validate: no gap for this defect.** The check exists (`zip-bytes-after-eocd`), fires under the default profile for `.docx` (word-valid) and under strict, and its message already prescribes the right repair. One correction to the analyst report I re-verified: the claim that "the default profile does not check the ZIP envelope" and "default run → All validations PASSED!" does **not** reproduce at this revision — the `.docx` default *is* word-valid (`src/scripts/office/validate.ts:167-173`), `runsWordPackageChecks` includes word-valid and strict (`src/scripts/office/validate.ts:1381-1383`, wired at `:567`), and my default run reports the error (exit 1). Only an explicit `--profile lenient` passes, which is documented, intentional behaviour for unmigrated callers (`src/scripts/office/validate.ts:1375-1383`). The report's citation `validate.ts:195-209` for the gate is stale — those lines are the `deadlineMs` option docs. An optional future enhancement (not a gap): an `--auto-repair` arm that truncates a packed file after its EOCD record.
- **No producing-tool bug in this repo's lanes:** no redline generator touched these bytes; the file entered the corpus already broken.
