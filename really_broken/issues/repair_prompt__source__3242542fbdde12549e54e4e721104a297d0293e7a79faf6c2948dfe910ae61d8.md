## Violation 1 — `zip-bytes-after-eocd`: seven undeclared bytes after the EOCD record

**Site:** the ZIP envelope, after the last record — no package part is involved.

`od -A d -t x1 -j 38471` of the packed file (run this session):

```text
0038471    50  4b  05  06  00  00  00  00  0f  00  0f  00  be  03  00  00
0038487    89  92  00  00  00  00  0a  0a  0a  0d  0a  0d  0a
0038500
```

- EOCD signature `50 4b 05 06` at offset 38471; 15 entries; central-directory
  size `0x3be` (958); central-directory offset `0x9289` (37513). 37513 + 958 =
  38471, so the record abuts its central directory — the archive itself is
  coherent.
- The comment length is the `00 00` at offsets 38491–38492, so the record ends
  at offset 38493. The file continues to 38500 with `0a 0a 0a 0d 0a 0d 0a`
  (LF LF LF CR LF CR LF) — seven bytes the record does not declare.

**Rule.** No bundled XSD governs the ZIP envelope (all schemas under
`src/scripts/office/schemas/` describe package parts). The rule is the ZIP
APPNOTE "End of central directory record" definition — the record's comment
length declares, and bounds, the end of the archive — implemented by the
repo's own check, which I read and ran:

- `src/scripts/office/zip-bytes-after-eocd.ts:151-152` — "`/** Count of bytes
  after the end-of-central-directory record past its declared comment. */`",
  `countZipBytesAfterEocd`.
- `src/scripts/office/checks/package.ts:16-32` — check id `zip-bytes-after-eocd`
  (group `package`, archive-only); message: "`ZIP end of central directory is
  followed by ${trailing} undeclared byte(s). Word offers to recover the
  document. Remove the bytes after that record; a comment whose length is
  declared in the record is not this defect.`"
- Registered in the default registry at `src/scripts/office/checks/index.ts:146`.
- CLI explanation at `src/scripts/office/validators/word-error-explanations.ts:129-130`.

The lenient pass plus the clean `document.xml` confirm the parts carry no
defect: the sole problem is the envelope. (Correction to the analyst notes: on
this branch the plain default invocation already reports the error — the DOCX
default profile is word-valid, and explicit `--profile lenient` is the run that
passes. The check's reach is unchanged: it fires under word-valid and strict.)

**Proposed fix (repair — broken source document):** truncate the file to its
first 38,493 bytes, i.e. delete the seven trailing bytes `0a 0a 0a 0d 0a 0d 0a`
so the EOCD record (with its declared comment length of 0) is the last thing in
the file. Do not touch any byte before offset 38493. Alternatively, if the
trailing bytes must be kept as content, raise the EOCD comment-length field at
offsets 38491–38492 to declare them — but they are newline junk, not a comment,
so truncation is the right repair. The seven bytes look like stray text-mode
newline writes appended after the ZIP stream; whatever pipeline step appended
them is the origin of the defect.

**Fix target:** `repair` — the source document's ZIP envelope, not any
producing tool in this repo's lanes and not docx-validate: the check exists,
is registered, and fires with the exact count.

## Where the fixes belong and why

- **repair (this issue's actionable fix):** the document. The proven assessment
  and the repo's own fixtures settle it: `tests/fixtures/working/
  package.zip-no-bytes-after-eocd.docx` (38,493 bytes) is byte-identical to
  this file's first 38,493 bytes — I compared them this session — and its
  hash-bound manifest observation is a clean open. Truncate to 38,493 bytes.
- **Not docx-validate:** `zip-bytes-after-eocd` detects the defect with the
  correct count and a correct, actionable message. No validator gap, no false
  positive. (If anything, this issue documents that lenient intentionally does
  not run ZIP-envelope checks — per the repo's documented mode policy, not a
  bug.)
- **Not a generator bug:** lane category is `source` — the defect predates any
  redline tool.
