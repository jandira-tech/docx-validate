## Violation 1 — `zip-bytes-after-eocd`: 2,434 undeclared bytes after the EOCD

**Offending bytes** (re-verified this session, `python3 -I` struct parse of the packed file):

- File size 362,096. EOCD signature `PK\x05\x06` at offset **359,640** — the only EOCD in the file (`data.rfind` and forward scan both return just this one).
- EOCD fields: 28/28 entries, central directory size 1,818 at offset 357,822 (`357822 + 1818 == 359640`, plain single-archive layout), **comment length 0**.
- Record ends at 359,662. Bytes **359,662–362,095 (2,434 bytes)** follow it, undeclared:

  ```
  3c 21 44 4f 43 54 59 50 45 20 68 74 6d 6c 3e 0a  <!DOCTYPE html>\n
  3c 68 74 6d 6c 20 6c 61 6e 67 3d 22 70 6c 2d 50 4c 22 3e  <html lang="pl-PL">
  … <title>WordPress &rsaquo; Błąd</title> …
  … <div class="wp-die-message">test</div></body>\n</html>\n\t\r\n\r\n
  ```

- No `PK\x03\x04`, `PK\x01\x02` or `PK\x05\x06` occurs inside the trailing blob — this is the **plain appended-HTML variant**, not the concatenated-archive variant.
- The 28 unpacked parts are intact: `word/document.xml` is well-formed (`xmllint --noout` passes, Transitional `w:document` root), and the word-valid run raises no part-level error. The defect is invisible in the unpacked view by nature — envelope checks are archive-only (`src/scripts/office/checks/package.ts:7-9`).

**Rule** — no bundled XSD covers the ZIP envelope (`grep -ril zip src/scripts/office/schemas/` matches only `SOURCES.md`). The governing spec is the PKWARE APPNOTE, which OPC (ISO/IEC 29500-2, Physical Model) incorporates for the package container; re-fetched this session from `https://pkware.cachefly.net/webdocs/casestudies/APPNOTE.TXT`:

- §4.3.1: *"A ZIP file MUST have only one 'end of central directory record'."*
- §4.3.6 (Overall .ZIP file format): local file headers + file data, then central directory headers, then the zip64 EOCD records, **then the end of central directory record** — the EOCD is the final record of the archive.
- §4.3.16 (End of central directory record): after the fixed fields, the record's only trailing payload is `… .ZIP file comment length (2 bytes) … .ZIP file comment (variable size)`. With the comment length stored as 0, nothing may follow the record's 22 fixed bytes — these 2,434 bytes are outside the archive's declared extent.

**Check** (already in docx-validate — fires correctly): `zip-bytes-after-eocd`, error severity, `src/scripts/office/checks/package.ts:16-33`; byte counting in `src/scripts/office/zip-bytes-after-eocd.ts:152-180`; runs under `word-valid` and `strict` (`runsWordPackageChecks`, `src/scripts/office/validate.ts:1381-1383`), which makes the **default** `.docx` run (word-valid) catch it.

**Proposed fix (repair)**: delete bytes 359,662–362,095 — truncate the file to its first 359,662 bytes so the EOCD record is the last record in the file, every preceding byte unchanged. Rewriting the EOCD comment length to 2,434 would also satisfy the record's grammar but keeps a bogus error page inside the container and mutates the record itself; truncation is the minimal change the proven assessment validated in Word. Origin note for whoever re-fetches: the appended page is a WordPress `wp_die()` output and the document is Polish — the serving host concatenated its own error page after the complete download, so a re-download may or may not reproduce the corruption.

**Fix target**: `repair` (broken source document).

## Where the fixes belong and why

- **repair** — the source document's *container* is corrupt; the document's 28 parts are fine. Nothing in docx-validate or any redline generator produced these bytes. The fix is byte-level truncation of the fetched artifact (or a clean re-download), not a code change.
- **Not docx-validate** — the validator neither misses nor misreports this: the default word-valid run reports exactly one error, `zip-bytes-after-eocd`, with the exact byte count (2,434), and its explanation text already prescribes deleting the bytes (`src/scripts/office/validators/word-error-explanations.ts:129-131`). Explicit `--profile lenient` passing is documented, intentional behaviour (`validate.ts:1376-1383`).
