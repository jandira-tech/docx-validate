## 2026-05-22 - Avoid xpath ancestor:: resolution in @xmldom
**Learning:** Using `xpath` (from the `xpath` NPM package) with `@xmldom/xmldom` is extremely slow when querying with the `ancestor::` axis (e.g., `.//w:p[not(ancestor::w:txbxContent)]`). This causes significant performance bottlenecks for large documents because it traverses the tree for every matched element dynamically instead of just caching parent lookups.
**Action:** When complex ancestor exclusions are needed on large node lists, rely on native DOM APIs (`getElementsByTagNameNS`) combined with a fast `parentNode` while loop in JavaScript. This simple rewrite improved paragraph counting performance by nearly 100x.
## 2026-05-23 - Avoid xpath descendant queries in @xmldom
**Learning:** Using `xpath` with `@xmldom/xmldom` to perform descendant queries like `.//w:del//w:t` is extremely slow. Since `xpath` evaluates by dynamically walking the tree structure on each execution instead of leveraging native DOM caching optimizations, even simple operations on large documents create severe bottlenecks (e.g. 1.5s vs 21ms for DOM queries).
**Action:** When querying for nested sub-elements, use native DOM APIs (`getElementsByTagNameNS`) over the required namespace prefixes. If a query mimics an XPath node-set and deals with potentially nested duplicate occurrences, ensure you iterate node results into a `Set<Node>` to cleanly emulate xpath's non-duplication properties and avoid iterating the same elements multiple times.
