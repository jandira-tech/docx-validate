## [Unreleased]

### Added

- Pin partial/full error-subset parity for case, NFC/NFD and NUL-bearing ZIP names under Word-valid and lenient (#423). The collision fallback added in #454 already fixes the reported subset defect; this adds regression coverage without changing validation policy.

- Registered the `zip-bytes-before-archive` package check for bytes in front of the archive JSZip loads — a prepended ZIP, junk, or a self-extractor stub, with relative or absolute offsets. Word 16.115 offers to recover every prefixed package probed, so it is a blocking error under strict and Word-valid DOCX/DOCM; lenient runs no envelope check ([#464](https://github.com/jandira-tech/docx-validate/issues/464); probe session 14 in [docs/plans/evidence/word-probes-2026-10-24.md](docs/plans/evidence/word-probes-2026-10-24.md)). A concatenated `[zip][docx]` is now reported once, by the new check; `zip-bytes-after-eocd` keeps genuine trailing data, measured from the loaded archive's own record.
- Registered `word-part-content-type-generic` content-types check for DOCX/DOCM: a part Word reads — the main document, or a part its relationships of type styles, settings, fontTable or webSettings name — whose content type resolves only through `<Default Extension="xml" ContentType="application/xml"/>` is reported at the part's path, naming the relationship type and the content type the part needs. Resolution follows ECMA-376 Part 2 §10.1.2.4 (exact Override first, then Default), so a part with a specific Override — right or wrong — is out of scope, and numbering and customXml stay silent until a probe observes them. Word 16.115 offers to recover the package for all five parts probed typed only by the generic Default, and opens every proper-Override control clean, so the finding is an error, and Word-blocking, under word-valid, an error under strict (Part 1 gives each of these parts its own content type; a main document is not reported twice there when `ct-undeclared-part` rejects that same path), and a warning under lenient ([#432](https://github.com/jandira-tech/docx-validate/issues/432)).

- Registered `opc-part-name-escaped-unreserved` package check for OPC [M1.8], including packed and directory inputs, full and partial runs, and diagnostics before extraction. Escaped unreserved characters in stored names are errors under strict and Word-valid DOCX/DOCM, and warnings under lenient and Word-valid PPTX/XLSX ([#408](https://github.com/jandira-tech/docx-validate/issues/408)).

- Diagnose equivalent stored part names and multiple content-types stream spellings with the selectable `opc-equivalent-part-names` package check. Full runs report it before extraction. Strict, and word-valid for DOCX/DOCM, report an error, because Word 16.115 offers recovery for every duplicate spelling probed (case, unreserved escape, backslash, two streams), even with identical bytes. Lenient, and word-valid for PPTX/XLSX, warn ([#351](https://github.com/jandira-tech/docx-validate/issues/351)).

- Named Word rules in `WORD_RULE_CHECKS`, prerequisite scheduling with per-part XML gating, `--quick`, `--checks`, `--list-checks`, `--strict`, `--json`, and shared API execution metadata ([#267](https://github.com/jandira-tech/docx-validate/issues/267), [#271](https://github.com/jandira-tech/docx-validate/issues/271), [#272](https://github.com/jandira-tech/docx-validate/issues/272), [#306](https://github.com/jandira-tech/docx-validate/issues/306), [#307](https://github.com/jandira-tech/docx-validate/issues/307)).
- Structural Word checks for misplaced content/properties, incomplete drawings/pictures, unknown elements, namespace-less links, and empty custom-property filetimes replace XSD-message heuristics ([#269](https://github.com/jandira-tech/docx-validate/issues/269)).
- Advisory checks for math revisions, shading colors, grid-column attributes, cell-margin order, required table/page properties, and textbox namespaces ([#235](https://github.com/jandira-tech/docx-validate/issues/235), [#213](https://github.com/jandira-tech/docx-validate/issues/213), [#210](https://github.com/jandira-tech/docx-validate/issues/210), [#209](https://github.com/jandira-tech/docx-validate/issues/209), [#211](https://github.com/jandira-tech/docx-validate/issues/211), [#212](https://github.com/jandira-tech/docx-validate/issues/212), [#214](https://github.com/jandira-tech/docx-validate/issues/214), [#244](https://github.com/jandira-tech/docx-validate/issues/244)).
- Optional `--verify-word` / `verifyWord` verification with macOS Microsoft Word, exact-byte temporary copies, classified outcomes, hash/version/platform/timing metadata, and document-scoped cleanup ([#273](https://github.com/jandira-tech/docx-validate/issues/273)).
- Packaged `docx-validate` bin at `dist/cli.mjs`, a silent library entry, and an installed-package smoke covering imports, validation, schema assets, and CLI help ([#314](https://github.com/jandira-tech/docx-validate/issues/314), [#274](https://github.com/jandira-tech/docx-validate/issues/274)).
- Hash-bound manifest Word observations with preserved history and independent `fixtures-all-word-valid` regression expectations; unknown, timeout, and stale evidence is excluded from accuracy counts ([#274](https://github.com/jandira-tech/docx-validate/issues/274), [#313](https://github.com/jandira-tech/docx-validate/issues/313)).
- Per-module coverage gates through `test:coverage-gate` and CI, plus a `Coverage: N% lines, M% branches` summary on every coverage-enabled Vitest run, including failures ([#266](https://github.com/jandira-tech/docx-validate/issues/266), [#271](https://github.com/jandira-tech/docx-validate/issues/271), [#274](https://github.com/jandira-tech/docx-validate/issues/274)).

### Changed

- `word-main-document-part` now rejects multiple internal package `officeDocument` relationships under Word-valid and strict for DOCX/DOCM, naming every relationship `Id` at `_rels/.rels`. Word 16.115 offers recovery for distinct well-formed targets and for a repeated target (Word probes session 15, s15b/s15d; [#515](https://github.com/jandira-tech/docx-validate/issues/515)). Transitional and Strict types count together (mixed pairs are inferred, not probed); External relationships remain excluded. Single relationships and orphan main-typed parts retain their verdicts. Quick and named runs share the full run's finding and severity.

- Word-valid judges `xml-syntax`, `xml-undeclared-prefix` and `xml-encoding` by reachability, not by folder ([#437](https://github.com/jandira-tech/docx-validate/issues/437)). Word 16.115 opens clean an unreferenced truncated `word/xtra.xml` — even with its own Override — and one named only by a relationship of an unknown type, and a related-but-unused malformed footer, comments or footnotes part; it offers recovery for a malformed part a main-document relationship of an eagerly parsed type names (styles, settings, fontTable, webSettings, numbering) wherever it is stored, for a `customXml` item named by a document relationship, and for a footer or comments part the document references. The reached set is computed once per run (`wordReadParts`, beside `propertiesParts`) and shared by full, quick and named runs and by the staging-failure fallback (#381, [#488](https://github.com/jandira-tech/docx-validate/issues/488)); parts under `word/` named by an unobserved Office relationship type (theme, header, chart, …) keep blocking, so no new false negative opens. A malformed part named by nothing now warns under word-valid instead of erroring; strict and lenient are unchanged. Evidence: `docs/plans/evidence/word-probes-2026-10-24.md`, sessions 3c, 4, 5, 8b and 9a.

- **Breaking:** DOCX/DOCM default to `word-valid`; pass `--profile lenient` or `{ profile: "lenient" }` for the previous policy. PPTX retains its lenient default. DOCX/DOCM Word-valid runs structural checks without document XSD validation, with `schemaCompleted: false` and an `xsdWalk` that has not started; strict includes the Word rules and applicable schemas ([#266](https://github.com/jandira-tech/docx-validate/issues/266), [#269](https://github.com/jandira-tech/docx-validate/issues/269), [#271](https://github.com/jandira-tech/docx-validate/issues/271)).

- Document that Word-valid's `xml-encoding` blocking also covers real encodings libxml2 cannot decode (`macintosh`, `x-mac-cyrillic`, `IBM866`, `UTF-7`), which Word 16.115 refuses too ([#410](https://github.com/jandira-tech/docx-validate/issues/410)). The third real-Word session is recorded in `docs/plans/evidence/word-probes-2026-10-24.md`.

### Fixed

- Direct DOCX and PPTX validators return one `package-extract-failed` error for a refused directory stored name instead of rejecting with `PackageViewError`. The message matches `validate()` under every profile, before XML checks; programming errors still propagate ([#548](https://github.com/jandira-tech/docx-validate/issues/548)).

- Unreadable packed inputs report `Cannot read` with the system error instead of describing the archive as encrypted, corrupted or truncated. Full and partial runs keep the same `package-open-failed` error, with no checks executed or Word verifier invoked ([#547](https://github.com/jandira-tech/docx-validate/issues/547)).

- Word-valid now follows a main-document `glossaryDocument` relationship to the glossary's own relationships part and reads the header or footer its `w:headerReference` / `w:footerReference` names by `r:id` ([#539](https://github.com/jandira-tech/docx-validate/issues/539)). Word 16.115 offers to repair a package whose `word/glossary/header9.xml` is malformed when a glossary `w:docPartBody` `w:sectPr` references it — probe session 16 (2026-10-24), `ar-header-ref-in-glossary-malformed` — while the well-formed control opens clean, so the glossary's referenced header or footer now blocks `xml-syntax`, `xml-encoding` and `xml-undeclared-prefix` under word-valid wherever it is stored; the footer is inference from the header observation. An unparseable glossary leaves usage unknown and its lazy targets stay reached, as an unparseable main does (#536). The glossary's comments, footnotes and endnotes relationships and its own relationships part are unobserved — session 16 also opened `ar-endnote-ref-in-footnote-malformed` clean — and stay unreached. Strict and lenient are unchanged; full, quick and named runs agree (#381).
- Word 16.115 offers to recover the package when a Word-read part's content type carries a MIME parameter, even when the media type is the part's own Word type (`; charset=utf-8` on the main document and styles; probe session 16, 2026-10-24, the table living with the issue). `word-part-content-type-generic` now judges the media type — everything before the first `;`, ASCII case-insensitively — so `application/xml; charset=utf-8` counts as generic and the finding names the declared value; the parameterized spellings on settings, fontTable and webSettings are inference from the same resolution, as #517's were. The new registered `word-part-content-type-parameter` check reports a content type whose media type is the expected Word type but which carries any parameter — one finding per part, naming the declared value and its Default/Override source — scoped to the main document (all four main types) and styles under word-valid and strict, both Word-blocking; lenient warns. Settings, fontTable, webSettings and the Part 1 part types are unprobed for a parameterized type and stay silent; the #535 strict suppression for a Default-typed main applies unchanged ([#540](https://github.com/jandira-tech/docx-validate/issues/540)).

- Keep lazy related parts reached when the main document fails byte-level XML checks even if its recovered DOM parses. An unsupported main encoding can no longer demote a malformed header or endnotes diagnostic to a warning; the same usage decision serves full, partial and staging-fallback runs ([#536](https://github.com/jandira-tech/docx-validate/issues/536)).

- Strict retains `word-part-content-type-generic` for a Default-typed main part unless `ct-undeclared-part` actually reports an error for that same path. Main parts with non-XML names or stored under `docProps/` now fail strict as they fail word-valid; quick and named word-valid checks agree ([#535](https://github.com/jandira-tech/docx-validate/issues/535)).

- The stored-name walk refuses a central directory JSZip refuses. A field inside an extra region that fits the buffer can declare more data than the buffer holds — JSZip's `readExtraFields` bounds each field's `readData` against the whole buffer and throws, while the walk bounded only the record's region extent and still returned names, contradicting its "undefined exactly where JSZip's reader throws" contract. The walk now bounds each extra field's declared length, the same scan `zip-bytes-before-archive` uses, so the names view is undefined there too ([#525](https://github.com/jandira-tech/docx-validate/issues/525)).
- `zip-bytes-before-archive` no longer claims a prefix for a package JSZip never opens. The measure stopped at the local-signature read, but JSZip's `readLocalPart` keeps reading — the fixed 30-byte header, the local name and extra field, the central-declared compressed stream, and a known compression method (store or deflate) — and an archive whose local part throws there is refused outright. A self-extractor-shaped specimen whose first record's local header points at a local signature appended as the EOCD comment used to report "N byte(s) precede the ZIP archive" beside `package-open-failed`; it now reports only the refusal, full and partial runs alike, and the measure is undefined exactly where JSZip's reader throws ([#524](https://github.com/jandira-tech/docx-validate/issues/524)).
- Re-keying a prefixed ZIP64 package no longer produces an archive JSZip refuses. The rewrite wrote the ZIP64 locator's record offset rebased past the prefix, but JSZip tests that field before applying its rebase, so on a prefixed package the check missed the real record and fell back to the last ZIP64-record signature — one the verbatim EOCD comment can hold — and a package JSZip loads (a self-extractor whose locator names the record absolutely, with a fake record signature in the EOCD comment) failed validation with `package-open-failed`. The written offset now names the moved record absolutely, the way JSZip consumes it, so the prefix stays a prefix and the package keeps loading ([#521](https://github.com/jandira-tech/docx-validate/issues/521)).
- A relationship type with an extra path segment inside an Office relationship-type namespace no longer reads as its last segment: `…/relationships/custom/styles` made its target a `styles` target for `word-part-content-type-generic` (a Word-blocking error under word-valid), an eagerly parsed part for word-valid XML blocking, and an "observed" type that skipped the `word/`-folder rule. One helper now returns a segment only for an exact namespace-plus-segment type, so such a type falls to the unobserved-types rule like any other unknown Office type: its `word/` targets keep blocking, and it reaches nothing outside `word/` ([#519](https://github.com/jandira-tech/docx-validate/issues/519)). Word 16.115 opens clean a part named only by a relationship of an unknown type (probe session 5b, `437-unknown-type-rel-malformed`, type `urn:x:unknown`); the extra-segment case inside the Office namespace is unprobed, so the conservative `word/` rule stands.
- The `ct-markup-compatibility` message now lists a Markup Compatibility element before its own attributes, as DOM document order has it (WHATWG DOM: an attribute is `FOLLOWING | CONTAINED_BY`, 20, against the element owning it). Detection, severity and verdicts are unchanged; only the order of the entries in the message differs ([#526](https://github.com/jandira-tech/docx-validate/issues/526)).
- A malformed percent-escape no longer hides a later percent-encoded `iunreserved` character: the Part IRI [M1.8] scan now resynchronizes at the next octet after a failed UTF-8 decode, so `/word/x%E9%C3%A9-é.xml`, `/word/x%C0%AF%C3%A9-é.xml` and `/word/x%C3%C3%A9-é.xml` are reported as `ct-override-partname-invalid` ("must not percent-encode an unreserved character (OPC [M1.8])") instead of passing ([#523](https://github.com/jandira-tech/docx-validate/issues/523)).
- `partNameViolation` now follows RFC 3987 §2.2's `ucschar` ranges exactly: the last astral block is `%xE1000-EFFFD`, not `%xE0000-EFFFD`, so a literal `U+E0000..U+E0FFF` in an Override `PartName` is no `ucschar` — it is in neither the RFC 3986 `pchar` nor the RFC 3987 `ipchar` set — and is reported as `ct-override-partname-invalid` ("must contain only RFC 3986 pchar characters") under strict and word-valid, while `U+E1000` and `U+EFFFD` stay valid ([#522](https://github.com/jandira-tech/docx-validate/issues/522)).
- `word-part-content-type-generic` names the `<Default>` the part's own extension actually resolved through, not always the `xml` one: a `word/styles.sty` covered by `<Default Extension="sty" ContentType="application/xml"/>` now reports the `sty` Default ([#504](https://github.com/jandira-tech/docx-validate/issues/504)).
- `word-part-content-type-generic` under strict now covers every Part 1 WordprocessingML part type a main-document relationship names — numbering, header, footer, endnotes, footnotes, comments and glossaryDocument — not only the five Word-probed parts: a `word/numbering.xml` typed only by `<Default Extension="xml" ContentType="application/xml"/>` is spec-invalid (ECMA-376 Part 1, 4th edition, clause 11.3) and now fails strict, while word-valid keeps judging only the probed parts until a probe observes more ([#506](https://github.com/jandira-tech/docx-validate/issues/506)).
- `word-part-content-type-generic` on the main document no longer advises only `application/vnd.openxmlformats-officedocument.wordprocessingml.document.main+xml` — following that advice on a `.docm` would turn the macro-enabled package into a macro-free document. The finding now names all four Word main-document content types ([#505](https://github.com/jandira-tech/docx-validate/issues/505)).
- `word-part-content-type-generic` now reports a covered part typed by any generic XML content type — `text/xml` by Default or Override and `application/xml` by Override, compared ASCII case-insensitively — instead of only the `application/xml` Default, and the finding names the declaration that produced the type. Word 16.115 offers to recover every probed spelling on the main document and styles; the spellings on settings, fontTable and webSettings are inference from the same resolution. A main document carrying a generic `Override` is also reported under strict now — it used to be dropped with the Default-typed one `ct-undeclared-part` covers — so strict reports every case word-valid reports ([#517](https://github.com/jandira-tech/docx-validate/issues/517); probe session 15, 2026-10-24).
- A stored file in a directory input that can never be read — a broken symbolic link, or a non-regular file such as a FIFO — no longer silently disappears from the package: `walkFiles` drops such entries, so the run judged the remaining parts and reported misleading relationship findings instead of saying the stored file cannot be read. The directory walk reports them, and full runs under every profile, quick, and named-check runs fail with `package-extract-failed` naming the stored file and the reason, never opening a FIFO, with the stored-names diagnosis still seeing every stored name ([#426](https://github.com/jandira-tech/docx-validate/issues/426)).
- `--auto-repair` on a directory input never writes outside the input directory through a symbolic link: a directory whose tree holds a link — a stored entry such as `word\document.xml` symlinked outside, or a symlinked directory segment — is staged under part names like a backslash input, and the staged write-back accepts only regular files whose resolved path stays under the input root. A refused destination reports a `repair-write-back-failed` error naming the part and its stored file, leaves the link and its target untouched, and the other repairs still apply ([#425](https://github.com/jandira-tech/docx-validate/issues/425)).
- Word-valid judges header, endnotes, theme and glossaryDocument parts by how Word reads them ([#516](https://github.com/jandira-tech/docx-validate/issues/516)). Word 16.115 reads a header the document references (`w:headerReference r:id` — an open error when malformed) and an endnotes part any `w:endnoteReference` uses (repair) wherever they are stored, and eagerly parses theme and glossaryDocument parts a main-document relationship names (repair for both) — probe session 15 (2026-10-24) — so all four are reached from the main document's relationships like the other observed types and their `xml-syntax`, `xml-encoding` and `xml-undeclared-prefix` findings block under word-valid wherever the target is stored: four false negatives outside `word/` closed. A related-but-unused header or endnotes part under `word/` opens clean in Word, so it now warns instead of erroring: two false positives closed. The four types leave the `word/`-folder rule for unobserved relationship types, which people, chart, image and the rest keep; when the main document does not parse, lazy parts stay reached, as before, so no new false negative opens. Strict and lenient are unchanged; full, quick and named runs agree ([#381](https://github.com/jandira-tech/docx-validate/issues/381)).
- Word-valid blocks `xml-syntax`, `xml-encoding` and `xml-undeclared-prefix` on each main document's own relationships part, wherever the main document is stored ([#514](https://github.com/jandira-tech/docx-validate/issues/514)). Word reads `word/_rels/document.xml.rels` to reach styles, settings, headers and footers: Word 16.115 offers to recover the package when it is zero bytes or missing its root end tag, so a malformed main-document sidecar is again a word-valid error, not a warning — the reachability model of [#437](https://github.com/jandira-tech/docx-validate/issues/437) had left it unreached because a sidecar is never a relationship target. The sidecar is found by OPC part-name equivalence, as the relationship readers find it; other parts' relationships parts keep their warning, and strict and lenient are unchanged. Evidence: probe session 15 (2026-10-24) of the Word probes recorded in `docs/plans/evidence/word-probes-2026-10-24.md` (sessions 1–14 in the file; session 15's table lives with this issue).
- An internal error after the archive loads is no longer reported to users as `package-extract-failed`: `ValidationContext.fromArchive` now wraps only the two failures a real extraction reports — the refused item name and the unreadable entry — in `PackageViewError`, and load failures in the new `PackageOpenError`; `contextFromArchive` reports only those two classified errors and lets any other error (a `TypeError` out of our own post-load code) propagate as an internal failure instead of wearing a file-defect code ([#427](https://github.com/jandira-tech/docx-validate/issues/427)).
- `validate()` no longer throws `EACCES` (or any read error) on a packed input it cannot read: a mode-000 file passes `fs.stat`, so the packed bytes are now read once, guarded, before any validation work. An unreadable input reports one error-severity `package-open-failed` — an archive that cannot be opened — with no check listed in `executedChecks`, identically under every profile and under `quick`/named selection ([#422](https://github.com/jandira-tech/docx-validate/issues/422)).
- Refuse distinct normalized part/folder spellings that collide under ASCII case folding and NFC normalization before extraction on every host, using the shared package-view guard. Full and partial runs now agree on `package-extract-failed` and run only stored-name/envelope checks for these refused views, eliminating host-dependent XML findings for case-colliding core/main parts (#441). Exact duplicates and slash/backslash aliases retain their existing entry choice; later extraction failures still merge readable findings (#454).
- Apply package-view placeability guards to directory inputs before full or partial validation. Literal backslash names with empty or dot-only segments now yield the same `package-extract-failed` issue in quick, XML-only and package-only runs as in full runs (#424).
- Preserve root `mc:Ignorable` namespace findings as `ignorable-undeclared` in DOCX/DOCM named runs and staging-failure fallback, with the full run's severity and count. Descendant-only `mce-unbound-prefix` findings retain their identity ([#499](https://github.com/jandira-tech/docx-validate/issues/499)).
- Suppress consequential `word-math-parse` findings in named DOCX/DOCM runs and full runs whose archive cannot be staged, preserving the full validator's positioned XML diagnostics ([#500](https://github.com/jandira-tech/docx-validate/issues/500)).
- The `--original` baseline archive is read from disk and loaded once per `validate()` run instead of once per XSD-failed part: `BaseSchemaValidator` memoizes the read bytes' `loadCentralNamedArchive` result for the run, and the DOCX original-document root shares it. A failed read still yields the empty error set and a load JSZip refuses still rejects — the shared rejection replays it to every part, so baseline-subtracted findings are unchanged ([#481](https://github.com/jandira-tech/docx-validate/issues/481)). Each run, and each direct `validateAgainstXsd()` call, starts from the `--original` as it is then, together with the original-document root (which had been cached for the validator's lifetime): a re-run on one validator no longer subtracts the previous run's baseline, keeps a missing original's empty one, or replays a refused original's rejection after the file is replaced ([#503](https://github.com/jandira-tech/docx-validate/issues/503)). The memoized archive and the DOCX original-document root now live in per-invocation async-local state rather than on the instance, so an overlapping `validate()` on one validator can no longer swap the baseline an in-flight run is still subtracting against — which had let a run report `valid: true` against an original that was not its own, or invent an error its own original shared ([#520](https://github.com/jandira-tech/docx-validate/issues/520)).
- `zip-bytes-before-archive` measures the archive JSZip loads, not the raw base field: a saturated local-header offset is resolved through the record's ZIP64 (0x0001) extra field as JSZip's `parseZIP64ExtraField` does — the 8-byte slot after any saturated size fields, read with the same 32-bit arithmetic — so a clean package using the spelling no longer reports a fabricated prefix, a real prefix in front of one is measured exactly, and a record JSZip throws on (no extra field, a too-short value, a negative effective offset) yields no measure ([#490](https://github.com/jandira-tech/docx-validate/issues/490)). The central-directory walk now also bounds each record's 46-byte fixed header, so a header cut off by the buffer end reads as nothing — where JSZip throws — instead of producing `NaN` fields and a `NaN byte(s) precede the ZIP archive` finding ([#498](https://github.com/jandira-tech/docx-validate/issues/498)).
- `zip-bytes-after-eocd` judges a prefix end-of-central-directory record by its fixed extent, not its declared comment: a prefix whose comment length reaches into the live archive is still reported once, by `zip-bytes-before-archive`, instead of also being counted as removable trailing bytes, and genuine trailing data behind such a prefix is still reported, measured from the loaded record ([#491](https://github.com/jandira-tech/docx-validate/issues/491)).
- The central-directory walk tolerates a ZIP64 declared record count that reads -1 (all-FF bytes) when records exist, as JSZip's `readCentralDir` does; the count still refuses when no record is found ([#492](https://github.com/jandira-tech/docx-validate/issues/492)).
- The `ct-markup-compatibility` message lists every Markup Compatibility element and attribute once per occurrence, in document order, instead of collapsing repeated tag kinds into one mention each; detection, severity and verdicts are unchanged. The README's [M1.19] sentence now names every check that judges the processed stream — `ct-override-partname-word-refused` and `word-part-content-type-generic` were missing ([#495](https://github.com/jandira-tech/docx-validate/issues/495)).
- An `mc:Ignorable` naming the content-types namespace itself no longer wipes the judged stream. The view the content-types checks and the full-run coverage/resolution passes read now understands the stream's own vocabulary — a package whose `<Types>` root carries `xmlns:t="…/content-types" mc:Ignorable="t"` no longer draws specious `ct-uncovered-part`/`ct-undeclared-part` findings telling the user to declare parts that are already declared; the package stays invalid through `ct-markup-compatibility` and the raw-stream schema walk. Relationships parts (`.rels`) read through the same view add the package-relationships namespace, so their relationships stay visible to the checks that read them (for example `word-duplicate-*-relationship`); Word-part processing is unchanged ([#493](https://github.com/jandira-tech/docx-validate/issues/493)).
- A `mc:Choice` without `Requires` — or with an empty or blank one — is no longer selected for the processed view: the selection now requires a non-empty `Requires` naming only understood namespaces (`schemas/mce/mc.xsd` declares `Requires` `use="required"`), so the well-formed `mc:Fallback` is taken instead, and nothing is selected when there is none. `mce-malformed` is still reported for such a Choice wherever it is reported today. Only views holding such malformed AlternateContent change — Word parts and the content-types stream alike — so in the content-types stream the declarations of the unselectable Choice (for example a `ct-override-partname-invalid` `Override` `PartName`) are no longer judged, and the Fallback's are ([#494](https://github.com/jandira-tech/docx-validate/issues/494)).

Under `lenient` they run neither the Word rules nor the ZIP-envelope checks. Naming one of those checks, or only groups made of them, is refused as a mode conflict, before the target is read, like every other mode conflict. (`--checks package` is not such a selection: the package group also contains `opc-equivalent-part-names` and `opc-part-name-escaped-unreserved`, which a lenient run executes.) Under `word-valid` a DOCX check's error that Word tolerates is a warning, through the same `isWordBlockingIssue` predicate the complete run uses, now in `validators/word-blocking.ts`. A malformed `docProps/app.xml` is then a warning in both runs ([#381](https://github.com/jandira-tech/docx-validate/issues/381)).
- `word-attached-toolbar-utf8` reports every referenced toolbar part that carries the UTF-8 replacement sequence, once each, instead of stopping at the first ([#323](https://github.com/jandira-tech/docx-validate/pull/323)).
- A partial run whose archive does not open lists in `omittedChecks` only the checks it did not select, as every other run does; a selected check the archive kept from running is no longer called an omission ([#337](https://github.com/jandira-tech/docx-validate/pull/337)).
- A complete Word-valid or strict run of a package that opens but fails to extract lists the ZIP envelope checks it ran in `executedChecks`, in registry order, instead of none ([#335](https://github.com/jandira-tech/docx-validate/pull/335)).
- A Word verifier that throws yields an `unavailable`, unsatisfied verification instead of rejecting `validate` ([#333](https://github.com/jandira-tech/docx-validate/issues/333)).
- A partial CLI run prints `Selected checks passed`, never `All validations PASSED!`, even when it omitted no registered check: a PPTX or XLSX `--quick` run used to claim a complete pass on a deck the full run rejects. An `Also not run:` line names the format validator's own rules, where a full run walks schemas the schema walk ([#339](https://github.com/jandira-tech/docx-validate/issues/339)), and for a DOCX given `--original` the redlining validation against it ([#353](https://github.com/jandira-tech/docx-validate/issues/353)).
- `profileWalksSchemas` takes the format: a PPTX walks its schemas under every profile, so a `word-valid` PPTX run now probes the XSD engine at startup, and an XLSX run, which compiles no schema, no longer does ([#341](https://github.com/jandira-tech/docx-validate/issues/341)).
- The `schemaCompleted` doc scopes "always false under `word-valid`" to DOCX/DOCM ([#340](https://github.com/jandira-tech/docx-validate/issues/340)).
- Let an open that overran its budget settle before the cleanup close, so Word is never left holding a document opened after its close ([#328](https://github.com/jandira-tech/docx-validate/issues/328)).
- Stamp `observedAt` and the crash-report open instant from wall time (`wallNow`, default `Date.now`) instead of the deadline clock, and stamp an unpacked directory's `unavailable` verification with the current time instead of the epoch ([#329](https://github.com/jandira-tech/docx-validate/issues/329)).
- Return `unavailable` when a Word dialog is already showing before verification, without opening or closing anything; dismiss dialogs raised by this run during macOS cleanup so later probes remain attributable ([#315](https://github.com/jandira-tech/docx-validate/issues/315)).
- `word-document-root` finds the main part behind an OPC-equivalent officeDocument target (`WORD/document.xml`, `word/%64ocument.xml`), which let a foreign main root pass Word-valid. The schema walk's main-part test compares canonical part names, so an escaped reserved character (`word%2Fdocument.xml`) no longer names `word/document.xml` ([#344](https://github.com/jandira-tech/docx-validate/issues/344)).

- `word-document-root` and the schema walk's main-part test resolve the officeDocument target through one shared resolver (`resolvePartName`), so they agree: a backslash target (`word\document.xml`) now names the main part for the schema walk too, and an ignored main root behind it is an error again rather than info. Of two equivalent entries, only the one the target names is main; `findEquivalentPart` picks it whatever order the names come in ([#349](https://github.com/jandira-tech/docx-validate/issues/349)). The schema walk resolves its main parts once per validator rather than walking the unpacked tree for every ignored root ([#355](https://github.com/jandira-tech/docx-validate/issues/355)), reads `\` as `/` in entry names as it does in targets, so a main part stored as `word/a\b.xml` stays main ([#357](https://github.com/jandira-tech/docx-validate/issues/357)), and `resolvePartName` returns `undefined` for a reference that is empty, names the package root or climbs above it ([#356](https://github.com/jandira-tech/docx-validate/issues/356)). A query or fragment in the target is dropped before it is resolved, as System.IO.Packaging does, so `word/document.xml#frag` still names the main part for both checks ([#361](https://github.com/jandira-tech/docx-validate/issues/361)), and the schema walk reads `_rels/.rels` as the package view does: under a backslash name and in UTF-16 too ([#362](https://github.com/jandira-tech/docx-validate/issues/362)). Both checks find the package relationships by OPC equivalence, so `_RELS/.RELS` names them too ([#364](https://github.com/jandira-tech/docx-validate/issues/364)). When several entries name one part (`_rels\.rels` beside `_rels/.rels`), the archive, the extracted directory and the schema walk keep the same one, whatever the entry order: the entry stored under the part name itself, otherwise the smaller name. Before, the archive kept whichever entry finished decompressing last (in practice the last in ZIP order) and the directory the last in sorted order, so a quick run and a full run could judge different main parts ([#366](https://github.com/jandira-tech/docx-validate/issues/366)). The full run's own checks list the walked files the same way, so they no longer judge an entry the package view drops ([#368](https://github.com/jandira-tech/docx-validate/issues/368)). The archive still reads every entry, so an unreadable entry rejects it even when another entry names the same part, as extraction does ([#369](https://github.com/jandira-tech/docx-validate/issues/369)). A full run extracts the package view itself: each part once, under its part name, with the entry the view keeps. A part stored only as `word\document.xml` is then schema-validated and finds its `.rels` sidecar, and a stray entry beside its part can no longer overwrite it on Windows ([#371](https://github.com/jandira-tech/docx-validate/issues/371)). A ZIP item whose name starts with a slash or names a drive (`/word/x.xml`, `\word\x.xml`, `C:/x.xml`) names no part. The ZIP format forbids such names, and System.IO.Packaging ignores them, so a quick run now refuses the package (`package-open-failed`) as a full run already did (`package-extract-failed`), on every platform ([#372](https://github.com/jandira-tech/docx-validate/issues/372)). When the filesystem holds two parts as one file (a case or Unicode-normalization variant on macOS APFS), the full run stops with `package-extract-failed` instead of judging the merged bytes ([#373](https://github.com/jandira-tech/docx-validate/issues/373)). The full run also stops when such a filesystem merges two parts' folders, because the later part would otherwise be judged under a name the package does not hold ([#376](https://github.com/jandira-tech/docx-validate/issues/376)). Names are judged as stored in the archive, before JSZip rewrites them, so `/../word/document.xml` is refused as a leading-slash name instead of loading as `word/document.xml`. An empty or dot-only segment (`word//x.xml`, `docProps\nested\..\custom.xml`) is refused as well, because OPC forbids it and the two views would otherwise judge different names ([#378](https://github.com/jandira-tech/docx-validate/issues/378)). The schema walk matches part folders and file names ASCII case-insensitively, as OPC compares part names, so parts under `WORD/` are schema-validated, after the same markup-compatibility processing as parts under `word/` ([#377](https://github.com/jandira-tech/docx-validate/issues/377)).
- `word-attached-toolbar-utf8` reports a toolbar part under the package entry its target names, so a backslash or case-variant spelling of a part already reported adds no second finding and no finding names a part that does not exist; a case-variant target alone now finds its part ([#350](https://github.com/jandira-tech/docx-validate/issues/350)). The check builds its equivalence index (`equivalentPartLookup`) once per run instead of scanning every entry for every reference ([#358](https://github.com/jandira-tech/docx-validate/issues/358)), skips an External `attachedToolbars` relationship, and drops a target's query before resolving it, so it no longer reports an entry that the relationship does not name ([#359](https://github.com/jandira-tech/docx-validate/issues/359)).

### Known limitations

- Of equivalent stored part names, the package view still validates one entry, chosen deterministically; the content of the others is not validated. Case/NFC collisions between distinct normalized part or folder names instead refuse the view before extraction on every host (#441; [#351](https://github.com/jandira-tech/docx-validate/issues/351)).

### Security

- Replace the quadratic XML pretty-printer suffix regex with a linear scan, preserving formatting while preventing repeated tag starts in comments from causing excessive work (CodeQL alert #2).

### Added

Broken/clean fixture pairs and 144 recorded Word assessments document the evidence ([#192](https://github.com/jandira-tech/docx-validate/pull/192)).

- Word-valid skips XSD when a cheaper check already rejects a document, and otherwise stops at the first surfaced Word-blocking schema error. Lenient and strict retain complete XSD walks. Schema-valid parts use a status-only WASM path; failures retain messages ([#191](https://github.com/jandira-tech/docx-validate/pull/191)).
- Redlining validation uses iterative DFS with mixed-namespace containment and drawing exclusions. Nested insertions emit one diagnostic per offending text node. End-to-end benchmark results are mixed; no fixed speedup is promised ([#194](https://github.com/jandira-tech/docx-validate/pull/194)).

- Guard temporary original-part extraction with the shared path-containment resolver and retain nested paths for schema selection ([#193](https://github.com/jandira-tech/docx-validate/pull/193)). This hardens the boundary; a critical exploit through normal JSZip loading was not demonstrated.
- Use stable DOM snapshots in mutation-sensitive loops and normalize PowerPoint notes relationship targets ([#190](https://github.com/jandira-tech/docx-validate/pull/190)).
- Preserve Word-blocking XSD errors beyond the reporting cap; keep schema/engine failures blocking; guard private WASM pointers, reuse callbacks, and fall back to public validation when the fast path is unavailable.

- Restore type-aware lint startup by declaring `oxlint-tsgolint`; align Vitest and coverage 5.0.1 with Vite+ 1.0.0; give cold-start fixture tests appropriate timeout budgets.

## [0.52.0] — 2026-10-06

Breaking under `0.x` conventions: the native `libxmljs2` addon is replaced by
`libxml2-wasm` and schema-load failures change severity — see `MIGRATION.md`.

### Added

- **`word-error-explanations` public module.** `WORD_ERROR_EXPLANATIONS` / `explainWordError` — plain-language, real-Word-probing-grounded explanations for the 19 issue codes the `word-valid` profile treats as Word-blocking. The CLI prints them as a `↳ …` line under each error when running `--profile word-valid`. Re-exported from the package root.
- **`ct-uncovered-part` OPC coverage check.** Parts matched by no `<Override PartName>` and no `<Default Extension>` in `[Content_Types].xml` are now flagged (previously only declarable XML roots and known media extensions were checked — extensionless media slipped through). `PartName`s are URI-decoded before comparison, and media-extension matching uses own-property checks only (`x.constructor` is not a media type).
- **`getElementsByTagNameAll`** — stack-based DFS walker replacing quadratic live-`NodeList` iteration for wildcard collection; `getElementsByTagNameNSAll` now uses the same O(N) traversal (one shared implementation, two entry points). New `tests/xml-helpers.test.ts` pins the contract, including the native root semantics (Document root ⇒ `documentElement` included; Element root ⇒ self excluded).
- **`MIGRATION.md`** with per-version breaking-change notes.
- CI runs a Node 24 + 26 matrix.

### Changed

- **XSD engine: `libxmljs2` → `libxml2-wasm`.** The native addon ships no Node 26 / ABI-147 prebuild and no longer compiles against Node's V8 headers; the wasm build has identical libxml2 semantics with no native compilation step. Compiled schema validators are cached per schema path (the cache stores in-flight load promises, so concurrent first loads compile exactly one validator; failed loads evict and retry; source documents are disposed even when compilation throws).
- **Schema-load failures are errors, not info.** Unloadable schemas now produce `severity: "error"`, `code: "xsd-schema-load-failed"` (was `info` / `xsd-schema-load-skipped`). A validator must not call a document valid against a schema it could not load. The known-noisy Dublin Core import in `opc-coreProperties.xsd` stays suppressed via `IGNORED_VALIDATION_ERRORS`.
- `BaseSchemaValidator.assertLibxmljsAvailable()` → **async** `assertXsdValidationAvailable()` (wasm initialises asynchronously); error prefix is now `XSD engine unavailable (libxml2-wasm)`.
- **Toolchain: `pnpm` replaces `bun`** (`packageManager: pnpm@12.8.2`); all dependencies updated to latest.
- **`src/index.ts` is hand-maintained.** barrelsby could not reproduce the curated named exports and silently destroyed them on regeneration; the `barrel` / `barrel:check` scripts are gone and the barrel is edited by hand.
- **Format settings moved** from `.oxfmtrc.json` into `vite.config.ts`'s `fmt` block so `vp check` and `pnpm run fmt` cannot desync; `fmt` / `fmt:fix` now go through `vp fmt`.

### Fixed

- **CI workflows actually run again.** `pnpm/action-setup` now executes before `actions/setup-node`'s `cache: pnpm` resolution (the old order failed every pnpm job with "Unable to locate executable file: pnpm" — CI had not run green on `main` since 2026-06-02). The validator-diff workflow resolves pnpm via `package_json_file` (its path-scoped checkouts leave no root `package.json`).
- Validator performance on large documents: del-first `collectDeletedRunText` with Set dedup across both Word namespaces, native-DOM `validateDeletions` (no `xpath` descendant queries), O(N) paragraph counting that skips text-box subtrees during traversal, single-pass redlining stripping.

### Security

- **Zip Slip** blocked at extraction (`resolveSafeZipEntry`: `path.relative` containment, prefix-slip-safe).
- **Path traversal in relationship targets** contained lexically and via realpath-based symlink-escape detection (`containRelationshipTarget`), for both absolute and relative targets.
- **Document IDs use `crypto.randomInt`** instead of predictable `Math.random`-derived identifiers.

### Removed

- `libxmljs2` (runtime + `allowBuilds` entry), `barrelsby` (dev), `.oxfmtrc.json`, the `barrel` / `barrel:check` scripts.

## [0.1.2] — 2026-05-04

### Security

- **LD_PRELOAD shim removed from the published bundle.** The
  `acceptChanges()` LibreOffice flow uses a runtime-compiled C shim that
  `LD_PRELOAD`s into `soffice` to work around `AF_UNIX` restrictions in
  sandboxed VMs. That pattern legitimately matches supply-chain malware
  heuristics in automated scanners (Socket.dev, etc.) — and they're
  correct to flag _unknown_ packages doing this. The shim source remains
  in `src/scripts/office/soffice.ts` for developers who run the CLI
  directly, but `src/index.ts` no longer re-exports `soffice.ts` or
  `accept-changes.ts`, so the bundler tree-shakes both files (and
  `SHIM_SOURCE`, `LD_PRELOAD`, `RTLD_NEXT`, `dlsym`, etc.) out of
  `dist/index.mjs`. `grep -E "LD_PRELOAD|SHIM_SOURCE|RTLD_NEXT|dlsym"
dist/index.mjs` returns zero matches.
- Added `SECURITY.md` with the disclosure policy and a detailed
  explanation of the shim pattern, where it lives, and how to verify the
  published bundle is clean.

### Added

- **`bun run release` checklist wrapper** (`scripts/release.ts`) that
  reads `.release-checklist.md`, prompts `[y/N]` for each unchecked
  item, and aborts on the first "no" before forwarding to `bumpp`. The
  checklist itself lives in `.release-checklist.md` and isn't hard-coded
  — projects edit the file to match their actual workflow. `--yes` skips
  prompts for CI.
- `CHANGELOG.md` (this file).
- `llms.txt` package summary for LLM-friendly tooling.
- CodeQL workflow (`.github/workflows/codeql.yml`).
- Codecov coverage upload step in `ci.yml`.
- README badges for CI / CodeQL / Codecov / npm / bundle size / types.

### Changed

- README "Programmatic use" section updated with a clearly-marked "Not
  in the package surface: LibreOffice helpers" subsection pointing at
  SECURITY.md and the source-checkout path for callers that need
  `acceptChanges()` / `runSoffice()`.
- `llms.txt` synced with the post-shim-removal API surface.

### Internal

- `package.json` `barrel` script now passes `--exclude` patterns for
  `scripts/office/soffice\.ts$` and `scripts/accept-changes\.ts$` so
  regenerating the barrel preserves the surface trim.
