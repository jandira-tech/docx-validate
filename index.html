    docx-validate

    docx-validate

    OOXML validators and redline/comment helpers for .docx and .pptx files. Portable Word checks by default for DOCX, with optional XSD validation and real Microsoft Word verification. TypeScript, ESM, runs under Node (managed with pnpm) for the neurotic developer.

    • Repo: jandira-tech/docx-validate
    • npm: docx-validate
    • Maintainer: jandira.tech — We are building legal tech. Jandira Technologies is the studio behind tools like Cicero (a legal workbench that turns messy inputs into redlines, issue lists, and memos), PII redaction models for Brazilian Portuguese, and AI/contract-drafting benchmarks. docx-validate falls out of that work — when redlines have to round-trip through Word, validating the OOXML directly beats trusting the renderer.
    • docs: https://jandira-tech.github.io/docx-validate/

    Conventions

    • File names: kebab-case (merge-runs.ts, not merge_runs.ts or mergeRuns.ts).
    • Modules: ES modules (import/export), no CommonJS.
    • Imports: relative paths between sibling modules; no path aliases.
    • XSD validation goes through libxml2-wasm behind the XsdValidator interface (src/lib/xsd-validator.ts).
    • DOM work goes through @xmldom/xmldom + xpath via lib/xml-helpers.ts (parseXml, serializeXml, prettyXml, getElementsByTagNameNSAll) — do NOT call DOMParser directly so the implementation stays swappable.
    • Temp dirs use the tmp package via withTempDir(async (dir) => { ... }) (see lib/run-cli.ts).
    • CLIs use commander. Wire each script with runCli(...) from lib/run-cli.ts.
    • Validation results: return the ValidationResult shape from lib/types.ts; do not invent per-validator shapes.
    • Tests: vitest, one test file per module, fixtures under tests/fixtures/.

    Running CLIs

    The installed package ships a docx-validate bin that runs the validator CLI (dist/cli.mjs):

    npx docx-validate <path>          # or: node node_modules/docx-validate/dist/cli.mjs <path>
    docx-validate --help              # prints only the validator's usage

    dist/index.mjs is the library entry only — running or importing it never starts a CLI.

    From source, every script is still its own tsx entry point:

    pnpm exec tsx src/scripts/office/validate.ts <path>
    pnpm exec tsx src/scripts/office/unpack.ts <path>
    pnpm exec tsx src/scripts/office/pack.ts <dir>
    pnpm exec tsx src/scripts/accept-changes.ts <path>
    pnpm exec tsx src/scripts/comment.ts <path>

    The comment CLI's commentId and --parent values must be canonical decimal integers from 0 to 9007199254740991 (Number.MAX_SAFE_INTEGER) with no leading zeros. 0 is accepted; 01, a sign, whitespace, and any larger integer are refused.

    Programmatic use

    The validator and packaged document helpers are available as plain function/class imports. The package's barrel (src/index.ts) is hand-maintained (the export * section and the four-class surface/jubarte helpers are curated). Only the exports listed there are reachable from the package root; the registry, scheduler, provenance, and verifier implementation modules remain source internals.

    Validate a .docx / .pptx

    import { validate } from "docx-validate";

    const result = await validate("./contract.docx");
    //                ^? Promise<ValidateRunResult>
    //                   { valid: boolean; issues: ValidationIssue[]; suffix: ".docx"; repairs: number }

    if (!result.valid) {
        for (const issue of result.issues) {
            console.error(`${issue.severity}${issue.path ? ` [${issue.path}]` : ""}: ${issue.message}`);
        }
    }

    DOCX and DOCM default to word-valid: no known Word-opening defect detected by the complete portable check set. This is a prediction, not an observed Word open. PPTX keeps the lenient default and its existing XSD validator. The Word-valid behavior below applies to DOCX/DOCM. Pass { profile: "lenient" } (CLI: --profile lenient) to retain the earlier DOCX policy.

    The PPTX slide and master checks judge every slide and slide master the presentation relates, wherever it is stored, beside ppt/slides/ and ppt/slideMasters/. These are notes-shared (a notes slide two slides relate, one slide relates twice (#1045), or the two stored spellings of one slide's relationships part each relate, as every stored spelling is judged (#1017, #1052)), slide-layout-duplicate (a slide with more than one slideLayout relationship), sldlayout-missing-rid (a master's sldLayoutId naming no slideLayout relationship) and sldlayout-missing-rels (a master with no relationships part). The presentation is the part the package's officeDocument relationship names (#1013). The two historical folders match as OPC compares part names, ASCII case-insensitively and with escaped unreserved characters decoded, so ppt/slides/%5Frels/ is one of them (#1037), and every stored spelling of two equivalent part names in them is judged (#1017). A master's relationships part is found under any equivalent spelling (#1018). Outside ppt/slides/, a slide's relationships part is judged only when the slide is stored. A related slide that is not stored has its own finding, the presentation's rels-broken (#1019). Under word-valid and strict, the three checks read a relationship as the slide walk does: exactly the Office notesSlide or slideLayout type, Transitional or Strict, and internal. So an External relationship, or a foreign type that merely contains the name, neither shares a notes slide, nor adds a layout, nor satisfies a sldLayoutId. Lenient keeps the historical reading, as it keeps nested relationships (#1051). Under word-valid and strict, rels-id-mismatch reads a PresentationML element's relationship type exactly too: the type, spelled Transitional or Strict, must be the Office segment the element expects in its real casing (slide, slideMaster, notesMaster, handoutMaster, slideLayout). Unlike the slide checks it does not read TargetMode. Before, it passed when the lower-cased last segment of the type merely contained the expected name, so a p:sldId naming a slideLayout relationship passed as slide. An element in another namespace, such as a foreign element in a p:ext sharing a PresentationML local name, keeps that reading, as lenient and DOCX do (#1058, #1061). Outside lenient the id walk reads the Strict relationships namespace too, so a Strict package's ids are judged: r:id for its type here, and r:id, r:embed and r:link for rels-id-missing. Lenient reads only the Transitional namespace (#1065, #1073). The two codes' severity differs by format under word-valid. For DOCX/DOCM they are warnings, because isWordBlockingIssue does not list them, so a dangling or mistyped id that no Word rule judges leaves the package valid; strict reports them as errors. PPTX has no word-valid severity policy, so under word-valid and strict they stay errors and the package is invalid (#1091, #1092). A master's sldLayoutId that sldlayout-missing-rid reports is one finding under word-valid and strict: the run drops the id walk's rels-id-mismatch or rels-id-missing copy of the same element and id, as DOCX hands a story reference's copy to its Word rule. That check reads only the Transitional r:id, so a Strict rs:id beside it keeps its own rels-id-missing. Lenient keeps both findings (#1093).

    The strict profile runs the Word rules and applicable XSD schemas. Schema conformance is stricter than Word openability. A leading BOM is at most a warning under every profile and never fails a document on its own:

    const result = await validate("./contract.docx", { profile: "strict" });

    Cross-check tracked changes against an original (the --original CLI flag):

    const result = await validate("./redlined.docx", {
        original: "./baseline.docx",
        author: "Alice",
    });

    Word-openability checks run without XSD. The path API retains its XSD walk trace:

    const result = await validate("./contract.docx", { profile: "word-valid" });
    console.log(result.xsdWalk); // { started: false, parts: [], eligible: 0 }
    console.log(result.metadata?.schemaCompleted); // false

    For DOCX/DOCM, the path API and document validator do not compile or walk XSD schemas under word-valid, so schemaCompleted is always false. Full lenient and strict runs walk eligible parts; a malformed part can stop a lenient run before XSD. The XML part list uses OPC-equivalent extensions: ASCII case is ignored and unreserved escapes are decoded, so .XML, .RELS and .%72els parts are seen by the passes that iterate that list and by the XSD walk. It also holds every other part [Content_Types].xml declares with an XML type (application/xml, text/xml, or an application/…+xml type), whatever its name: Word reads a part by its relationship and content type, so a main document stored as word/document.bin under the main document's Override is checked as word/document.xml would be, and Word 16.115 refuses it truncated (#620, session 32). Image types such as image/svg+xml are not XML parts here. DOCX relationships validation passes use the same OPC-equivalent .rels predicate. Relationship-id and hyperlink checks also resolve sidecars by OPC part-name equivalence in packed and directory inputs, including full, named and quick runs: a .RELS sidecar resolves like .rels, matching Word 16.115's clean open. An escaped stored name such as .%72els still fails full Word-valid and strict validation, and quick Word-valid runs, through opc-part-name-escaped-unreserved (OPC [M1.8]), even though sidecar lookup resolves it (#402). Named selections diagnose the escaped name when they include that check. Empty-part auto-repair retains its exact lowercase .rels scope. The trace describes the schema walk, not a Microsoft Word invocation. Under strict, ISO Strict OOXML parts use the bundled schemas/iso-strict/ schemas. Lenient skips those parts with the info-level xsd-strict-skipped; Word-valid emits no XSD skip issue because it runs no XSD. The walk sends a part to the schema its identity maps to. The glossary document's parts (word/glossary/*.xml) use wml.xsd, and the DrawingML diagram parts (diagrams/dataN.xml, layoutN.xml, quickStyleN.xml, colorsN.xml under word/, ppt/ or xl/) use dml-diagram.xsd (#628). A part with no mapped schema, such as customXml/item1.xml or a diagram's drawingN.xml cache, is not sent: xsdWalk.parts lists exactly the parts that were. Each such well-formed part draws one info-level xsd-no-schema issue naming it, so the parts the walk skipped can be audited; validity, xsdWalk and metadata.schemaCompleted do not change, lenient's --original comparison never removes it, and a malformed part, a Strict part lenient skips and a part the run's deadline never reached draw none (#628). A direct validateAgainstXsd() call on a validator parses each unmapped part before auditing it, so a malformed one draws none there either (#867). In a PPTX, the slides, slide layouts and masters, notes slides and masters, handout masters, legacy comments and tags one folder below ppt/ use pml.xsd, matched by folder and file name (#864). PowerPoint's modern comments (ppt/comments/modernComment_*.xml), whose root pml.xsd does not declare, are among the unmapped parts. Directly in ppt/, the five conventional names (presentation.xml, presProps.xml, viewProps.xml, commentAuthors.xml and tableStyles.xml) go to pml.xsd by name (#872). Any other part there is routed by its root element (#887): it goes to pml.xsd when that root is a global element declared by pml.xsd or a schema it imports or includes, for the part's conformance class, and draws the audit otherwise. A renamed main presentation or a relocated slide therefore keeps its check, while ppt/authors.xml and ppt/revisionInfo.xml, whose Microsoft roots no bundled schema declares, stay unmapped. Each schema walk reads the roots afresh (#902). Only the first base validateFileAgainstXsd call the walk's own active call makes for a part keeps that part's root, and only once; every other call reads it afresh, so a validator reused after a part is rewritten routes it by its new root (#910), and so does a second or nested call for the same part on the same validator (#941), a call for another part, a call from another validator, or one made after the walk's call settled by a task that call started (#926). That first call routes by the root its walk read, whatever a nested call or walk reads meanwhile: each walk and each call keeps its own roots (#949). A task that outlives its walk or call reads the root afresh, even when it calls _validateSingleFileXsd directly; before, it routed by the root the walk or call had read (#964). Each schema walk keeps its own trace and engine-failure count, and the walk that finishes last leaves its own on the validator, so a walk nested in another on the same validator no longer lists parts twice or loses the outer walk's engine failures (#943). The earlier basename routes (core.xml, app.xml, custom.xml, …) still come first. The CLI prints the finding with --json; its human output lists errors only.

    Named checks and quick checks use the same options in the path and byte APIs:

    import { readFile } from "node:fs/promises";
    import { Validate, jubarte, validate } from "docx-validate";

    const quick = await validate("./contract.docx", { quick: true });
    console.log(quick.metadata?.omittedChecks);

    Validate and jubarte.validate also forward profile, strict, schemasDir, xsdValidator, verifyWord, wordVerifier, and deadlineMs. Set suffix on byte APIs for formats other than their default .docx (for example, .pptx or .docm).

    • --quick / { quick: true } selects QUICK_CHECK_GROUPS: package, xml, content-types, relationships, tables, and drawings.
    • --checks tables,word-run-misplaced / { checks: ["tables", "word-run-misplaced"] } selects check ids or group names, plus prerequisites. Unknown ids and explicitly named checks for another format are configuration errors.
    • A partial run applies its profile as a full run does, so it never fails a package the full run passes. lenient runs neither the Word rules nor the ZIP-envelope checks: only archive-only checks and Word rules are refused — naming one, or only groups made of them, is a configuration error. Under word-valid, an error Word tolerates is reported as a warning.
    • --list-checks lists every registered id, group, format, and description without reading a file or starting XML/XSD engines. --help also needs no engine startup.
    • --strict / { strict: true } is shorthand for profile: "strict". Strict rejects partial selection; --quick and --checks are mutually exclusive. --strict also rejects an explicit profile other than strict. A partial run never repairs, so --auto-repair / autoRepair: true with --quick or --checks is refused rather than ignored (#652). API conflicts throw ModeConflictError; CLI configuration errors exit 1.
    • Partial runs perform no XSD validation and report omittedChecks. A successful partial run prints “Selected checks passed”, followed by counts, never “All validations PASSED!”, even when it omitted no registered check (a PPTX or XLSX registers only the envelope and XML syntax checks). An Also not run: line names what has no check id: the format validator's own rules, where a full run walks schemas the schema walk, and for a DOCX given --original the redlining validation against it. It does not establish full-document validity. Selections run the registered checks only, without the full validator's other checks or severity remapping.
    • --json emits { valid, issues, metadata } for a completed validation, including warnings and available locations. Exit status is 0 for valid and 1 for invalid; configuration/startup errors go to stderr. The path API also returns suffix, repairs, and xsdWalk, which are not included in CLI JSON.
    • --deadline-ms <ms> / { deadlineMs } bounds the whole run, counted from the call; the byte APIs count their temporary write too (#630). The bound is cooperative: each step asks the budget before it starts — the package stages, every named check, every rule of the DOCX or PPTX validator, every part of the schema walk, the redlining validation, and Word verification — and a step already running finishes, so a run overruns by at most its longest single step. With a deadline the DOCX validator's rules run one after another rather than all at once, so the budget can stop one between two others. When the budget stopped any step, the run is invalid and reports one error-severity validation-deadline finding naming what did not run: a run cut short is never a pass, whatever the steps that ran found (timeout > engine error > invalid > valid). The profile's severity policy still applies to what ran. metadata.deadline reports { budgetMs, notRun }. A schema walk the budget stopped leaves schemaCompleted: false and counts the parts it never reached in xsdWalk.notExamined. Word verification gets what is left of the budget, at most its own 45 seconds; once the budget is spent it does not run and is unavailable. The budget is a finite number of milliseconds, 0 or more (RangeError otherwise; the CLI exits 1). It cannot be combined with --auto-repair: a repair writes, and a deadline could stop it part-way.

    Full lenient and strict CLI runs first compile a small startup probe schema to check the XSD engine. This is separate from document validation and is not recorded in xsdWalk. Word-valid runs compile no schema, so they skip that probe, as do help, discovery, and partial runs (#318).

    The registry in src/scripts/office/checks/index.ts includes WORD_RULE_CHECKS, which full DOCX validation runs under word-valid and strict, alongside its other validators. Full lenient validation does not run those Word rules. A ValidationContext caches part bytes and DOMs per run. Checks declare requires; the scheduler runs prerequisites once, in registration order. xml-syntax gates by part: dependent rules skip malformed parts and keep judging well-formed parts. A failed prerequisite without part-scoped findings skips its dependents. A throwing check yields check-crashed. For unpacked directories, runChecks() marks archive-only checks unavailable; use packed input to check ZIP integrity.

    The complete named check catalogue is below. Each Word check except word-markup-compatibility uses its id as its finding code. Package checks are zip-bytes-after-eocd, zip-bytes-before-archive, zip-eocd-comment-overrun, opc-equivalent-part-names, opc-part-name-escaped-unreserved, opc-part-name-escaped-slash, opc-part-name-word-refused, and opc-item-name-refused; xml-syntax is the shared XML prerequisite. All word-* checks apply to DOCX/DOCM only. ct-duplicate-declaration, ct-override-partname-invalid, ct-override-partname-word-refused and ct-markup-compatibility apply to every package format; word-content-type-invalid, word-part-content-type-generic, word-part-content-type-inexact, word-part-content-type-mismatch and word-part-content-type-unrecognized apply to DOCX/DOCM only.

    zip-bytes-before-archive applies to DOCX/DOCM, PPTX, and XLSX package selections, including the package quick group, and reads the archive bytes before extraction. It reports the bytes in front of the archive JSZip loads — the rebase offset plus the lowest local-header offset as JSZip resolves it, so a prepended ZIP, junk with relative offsets, junk with the absolute offsets a self-extractor writes, and the ZIP64 spelling (a saturated offset whose 0x0001 extra field carries the value) all measure the same prefix — as one blocking error under strict and Word-valid. The measure is undefined exactly where JSZip's reader throws — the local header's extent, its name and extra fields (each bounded on its own read, so a small negative resolved size cannot mask a name/extra overrun), the central-declared compressed stream (bounded on both sides: stream past the buffer, or a compressed size that reads negative — the 32-bit field 0x80000000 or a ZIP64 0x0001 value below zero — sending the final read's index below zero), and a known compression method (store or deflate) are modelled too — so a package whose local part JSZip cannot read reports no prefix (#524, #555, #566).     mce-root-ignored An ignorable root disappears from the schema view. Informational for non-main parts; not emitted by the full Word-valid path.
    mce-main-root-ignored The required main document root disappears from the schema view. Error in lenient/strict; the Word view reports word-document-root for a missing main root.
    mce-extension-not-ignorable Office extension attributes lack an Ignorable declaration and are removed from the schema view. Warning from schema preprocessing; not emitted by the full Word-valid path.

    Under Word-valid and strict, full DOCX/DOCM runs retain root Ignorable findings once as ignorable-undeclared even when staging fails. Named Word-valid runs share that identity, severity and count. Descendant-only findings keep mce-unbound-prefix (#499).

    Strict bundles both Transitional and ISO Strict schema trees, with local Dublin Core imports. Strict does not subtract errors shared with original; only lenient retains that XSD behavior. No profile suppresses schema messages by their text: IGNORED_VALIDATION_ERRORS is empty (#1209). Strict preserves each schema error occurrence and available engine line. If preprocessing changes the view, the message marks the line as referring to the preprocessed view. Schema-load failures remain blocking xsd-schema-load-failed issues; arbitrary unmapped custom XML is outside schema eligibility.

    Optional real-Word verification is independent of portable checks:

    const observed = await validate("./contract.docx", { verifyWord: true });
    console.log(observed.metadata?.wordVerification);

    docx-validate --verify-word --json contract.docx

    The built-in verifier requires macOS, Microsoft Word, and Accessibility automation permission for the host terminal. It opens a uniquely named temporary copy of the exact input bytes, without repair. The matching document must remain open and dialog-free for the default 3-second observation period. The default launch, observation, and cleanup budget is 45 seconds, with up to 2 seconds reserved for closing the document. Cleanup closes that copy without saving and never quits or force-kills Word. Portable validation and Word verification both contribute to valid; requesting verification does not make a portable failure pass.

    wordVerification records requested, satisfied, outcome, fileSha256, platform, observedAt, observationMs, details, and available wordVersion and wordBuild. Outcomes are clean-open, repair-warning, open-error, crash, password-prompt, unknown-dialog, timeout, or unavailable. Only clean-open satisfies verification. Unavailable or inconclusive results make an explicitly requested run invalid even when issues contains no errors. An unpacked directory has no packed bytes to verify and returns unavailable; other platforms or missing Word also return unavailable. crash requires a Microsoft Word crash report written after this run's open; a Word process that vanishes without one (an external kill or quit) is unavailable (#305). The Word version and availability calls run inside the same budget as the rest of the run, so a hanging call ends as timeout instead of outliving it (#320). A verifier that throws is reported as unavailable with its message; validate does not reject because of it (#333).

    Before opening, the verifier observes Word once. If a dialog is already showing, it returns unavailable without opening or closing anything: that dialog cannot be attributed to this file. Verification needs exclusive use of Word: runs must not overlap and Word must not be in use, because a dialog that appears after the pre-open observation is attributed to this file (#331). macOS cleanup dismisses the Word dialog showing at close, preferring Cancel, No, then OK; under exclusive use that is the dialog this run's open raised. When the open itself overran its budget, cleanup first lets it settle within the rest of the budget, so a late open never lands after the close (#328). It does not relaunch Word after a crash. The source implementation (src/lib/word-verifier.ts) supports injected transport and clock dependencies, plus a wallNow source: observedAt and the crash-report open instant are wall time, independent of the deadline clock (#329); public validation options accept a wordVerifier callback for deterministic tests or a custom verifier.

    pack refuses symbolic links to files or directories inside the input directory, returning { ok: false, message } with the link's relative path using / separators and writing no output file (#1199).

    unpack checks every entry before it writes one (#675). It refuses, writing nothing, an entry whose stored name leaves the output directory, even one JSZip would load inside it (../evil.txt loads as evil.txt; #676), and an entry whose destination runs through a symbolic link already in the output directory. The output directory itself may be a link. When a read or write fails part way, unpack removes the files and folders it created, including the output directory when it created it; a file it overwrote keeps the new bytes. Messages print control and bidirectional formatting characters in entry names as \u{…} escapes.

    These helpers, and validate()'s auto-repair, keep every XML part in the encoding it is stored in (#866). The byte order mark, then the XML declaration, decide it: a UTF-16 part is written back as UTF-16 in its own byte order, with its byte order mark if it had one. An encoding pseudo-attribute a helper writes or rewrites in the declaration names UTF-16 beside a mark, and UTF-16LE or UTF-16BE without one, since XML requires the mark of a part declared plain UTF-16 (#878). A declaration with no encoding pseudo-attribute keeps none, as XML then reads the encoding from the mark, or UTF-8 when there is none (#888). A UTF-8 part is written without a byte order mark, as before. A part whose declaration names an encoding this package cannot decode (windows-1252, macintosh, …) is left byte-for-byte untouched, and addComment returns an error naming it instead of editing it, changing nothing in the tree. The auto-repair writers then neither count nor report a repair for such a part: writeXmlPart returns whether it wrote (#880), and a part's repairs reach the repairs count, and its verbose Repaired: lines, only after a write — a refused write never reached disk. Three repairs rename one value in several parts: repairCommentThreading, repairParaId and repairDurableId's hex rewrite. Each leaves every part it would write untouched when one cannot be decoded (#889) or written (#909); repairDurableId's independent numbering.xml renumbering still runs when its hex rewrite is refused (#911). A write that fails after that check stops the repair, which counts only the parts already written; before, it rejected repair() and validate() with the other part already changed. So does a write writeXmlPart refuses after the check; before, the repair went on writing the later parts with the new value, splitting the rename (#920). In repairDurableId a failed write of a numbering.xml carrying only decimal durableIds does not stop the hex rewrite, and its decimal renumbering runs whether the hex rewrite is refused by the check or stopped by a failed write; before, such a failed write between two hex parts split the rename (#925). A numbering.xml that also carries a durableId the hex rewrite renames is a hex part like any other: its failed write stops the remaining hex renames (#942). No other repair renames a value across parts.

    For a document's first comment, addComment relates the four comments parts from the relationships part of the main document _rels/.rels names (#906).     Result shape — ValidationResult

    import type { ValidationMetadata } from "docx-validate";

    interface ValidationIssue {
        severity: "error" | "warning" | "info";
        message: string;
        path?: string; // file path inside the unpacked dir, when applicable
        code?: string; // stable string ID; safe to switch on
        line?: number; // 1-based, when available
        column?: number; // 1-based, when available
    }

    interface ValidationResult {
        valid: boolean; // requested checks and any requested Word verification passed
        issues: ValidationIssue[];
        metadata?: ValidationMetadata;
    }

    ValidationMetadata has optional profile, executedChecks, omittedChecks, schemaCompleted, and wordVerification fields. executedChecks reports the registry ids a complete run executed (#319): lenient lists opc-equivalent-part-names, opc-part-name-escaped-unreserved, opc-part-name-escaped-slash, opc-part-name-word-refused, and opc-item-name-refused first, then xml-syntax and the rest; Word-valid and strict add the ZIP-envelope checks for a packed file and every Word rule whose prerequisites passed. A partial run lists the selected checks that ran, so an archive-only check is not listed for an unpacked directory. A missing target (ENOENT or ENOTDIR) throws Error: <target> does not exist; other access failures throw Error: Cannot access <target>: <system error>. The CLI prints that error on one line and exits 1 (#574). An archive that does not open fails with package-open-failed in every mode, and only its envelope checks are listed (#332). A packed file that cannot be read at all — a mode-000 file fs.stat still answers for — fails the same way, with no check listed (#422). Its message says Cannot read followed by the system error; the encrypted, corrupted or truncated archive explanation is reserved for JSZip refusals (#547). One that opens but whose package view cannot be read — a stored item name that places no part — judged on the central-directory name, never the local header's or the unicode-path field's (#445) — or an unreadable entry — fails with package-extract-failed, as the full run's extraction reports it (#413). Each stored item name that places no part is also its own error-severity opc-item-name-refused finding, and a full or partial run of a packed file still judges the archive's other entries. It leaves the refused central-directory records out, so an entry a refused .. name hid in the package view is judged by its own bytes. A full run stages those entries and validates them as it would a clean package, the format validator's own rules and the schema walk included, then adds the package-extract-failed error; xsdWalk and metadata.schemaCompleted describe that walk. When the host cannot stage those entries either, because its file system folds two of their names into one (APFS folds Å and å), the run reports one package-extract-failed, naming the refused name, beside what the archive's own checks find in them (#874). A partial run judges them with its selected checks only. A ZIP64 archive is judged the same way when its end records can move with the shrunk directory. Neither judges anything more when the remaining names still collide (#413), when a ZIP64 end record cannot move (it holds extensible data or declares less than its fixed 44 bytes, or is not adjacent to its locator; #875), or when bytes sit between a non-ZIP64 central directory and its end record, and a directory input judges only its names (#629). Directory inputs apply the same stored-name refusal before either full or partial validation: literal backslash names with empty or dot-only segments are refused with the same code and message (#424). Direct DOCXSchemaValidator.validate() and PPTXSchemaValidator.validate() calls also return an error-severity package-extract-failed for such refused directory names, with the same message as validate(); programming errors still propagate (#548). They also apply the same directory walk refusal for broken symbolic links, non-regular files, unlistable directories and symbolic-link loops under every profile, before running any part-content check (#557). For either refusal, direct validators include the same stored-name findings, in the same order and at the same profile-dependent severities, as validate() for the same path string, and list the stored-name checks they ran in executedChecks, as validate()'s metadata.executedChecks does (#572). Its stored entry names and archive bytes are still read. Selected opc-equivalent-part-names, opc-part-name-escaped-unreserved, opc-part-name-escaped-slash, opc-part-name-word-refused, and opc-item-name-refused checks and selected envelope checks (such as zip-bytes-after-eocd) run and report what the full run reports. Every other selected check needs the package's parts: it runs on the entries a refused item name leaves, as above, and is otherwise listed in omittedChecks (#420, #629). It is not a per-method execution trace. In the source scheduler, use runChecks().outcomes for individual passed / failed / skipped / unavailable statuses. omittedChecks names ids left out by selection and, when the package view cannot be read, selected ids that could not run. schemaCompleted records completion of the eligible schema walk without schema-load failures; it is separate from whether schema findings made the document invalid. wordVerification is present only when requested.

    Full validation accepts unpacked directories, including POSIX files whose stored names contain literal backslashes (for example word\document.xml). Such inputs are validated in a temporary copy under package part names (word/document.xml), using the same duplicate selection and extraction guards as packed inputs. Directories whose tree holds a symbolic link — a stored entry or a directory segment — are staged the same way: the stored bytes are read through the link into the package view, while the write-back never follows it (#425). A link whose target resolves outside the input root is not followed at all: the walk refuses it at the link's stored name (a symbolic link outside the input directory), so foreign files never become package parts, content outside the root never decides the verdict, and a link to an ancestor of the root is named at the link itself rather than under a path inside it (#576). A link that resolves inside the root keeps the behaviour above: the loop detection of #546 and the write-back refusal of #544. The bound fails closed: an input root realpath(3) cannot resolve is refused as an unreadable directory, and a link it cannot resolve is refused (a symbolic link the walk cannot resolve) rather than followed. A stored destination is refused when any path segment between the input root and that destination is a symbolic link. When several stored paths name one physical file and any of them reaches it through a link, the whole group is refused, so the link's target stays untouched and one physical file is never written twice (#544). A stored regular file whose link count is greater than one is also refused, because a hard-link alias may name a file outside the input directory (#545). Directories with ordinary forward-slash names and no links are validated directly. Validation leaves source files unchanged unless autoRepair: true / --auto-repair is used. For a staged directory, repairs write changed bytes back to each original stored file name and delete originals of parts removed by a repair; untouched files and dropped duplicate entries remain byte-identical. No forward-slash replacement files are added to the input directory. Quick and named-check runs continue to read the directory's package view directly (#374). A packed file (.docx/.docm/.pptx) is different: auto-repair runs on a temporary staged copy that is discarded, so the source file's bytes never change. The result then carries an auto-repair-staged-copy info finding — and the CLI prints the same sentence on its own line, after Auto-repaired N issue(s) when anything was repaired — disclosing that the repairs and the repair plan describe the staged copy (#649). It appears only when a repair ran: a packed .xlsx, which has no validators, and a packed file that cannot be extracted get none (#666).

    A stored file that cannot be read fails the run with package-extract-failed, naming the stored file — the package view cannot be staged. This includes a stored entry that can never yield part bytes at all: a broken symbolic link, or a non-regular file such as a FIFO, which is reported by its stored name instead of silently vanishing from the package (#426); a FIFO is never opened, so it cannot hang the run. A subdirectory the walk cannot list fails the same way, naming the directory — every stored file under it would otherwise vanish with it, leaving the run to judge the parts it can still see (#543; the input directory itself is named .). A directory is no stored file entry, so it contributes no name to the package view: it is named only in the package-extract-failed detail, and the stored-name checks never judge a name no package holds (#573). A symlink loop — a directory link whose target is already on the path into it, or a link chain that never resolves — is reported as a symbolic link loop at the link's stored name (word/self), not as a broken link under a synthetic multi-level path (#546). A link out of the input root fails the same way, naming the link's own stored name (#576). When several entries are unreadable, the message names them one clause each, in code-unit order — the order the file list uses — so the same input yields the same message on every host, whatever the host's locale collation is (#575). Full, quick and named-check runs report the same failure. (Under ordinary forward-slash names the direct path reads parts lazily, so the same file yields check-crashed warnings instead.) When a write-back cannot reach its stored file — a read-only file, one removed mid-run, or a stored file that is a symbolic link, whose root-relative path contains a symbolic-link segment, has more than one hard link, or resolves outside the input directory, whose target the write-back never touches — the run reports a repair-write-back-failed error naming the part and keeps writing back the remaining repairs; the stored file is left untouched. That error is profile-independent: a repair the caller asked for and did not get is an operational failure, not a property of the document, so no profile downgrades it (#428). repairs counts repairs applied to the package view, so a repair whose write-back failed still counts (#412).

    These write-back checks are not race-resistant. They inspect the stored path and inode, then later write by path; a symbolic or hard link swapped in between the check and the write can still be followed. The same check-then-use limit is documented by containRelationshipTarget; descriptor-based no-follow writes would be required to close that race (#545).

    Distinct normalized part names that collide under ASCII case folding and NFC normalization now refuse the package view on every host, before extraction (#441). The same guard includes folder prefixes (word/a.xml beside WORD/b.xml), so a staging filesystem cannot silently rename their parts. Full, quick and named runs report package-extract-failed with the same detail, run only applicable stored-name and envelope checks, and omit part checks. This is a portable staging policy, independent of whether the host filesystem is case-sensitive. It does not turn every OPC-equivalent spelling into a staging refusal: identical stored names and slash/backslash aliases that normalize to one part retain their existing entry selection; escaped spellings retain their existing OPC diagnosis.

    A later extraction failure on an otherwise readable view still merges the archive-backed findings under the selected profile (#454). For example, the host may refuse an overlong filename. Already-run stored-name and envelope checks are not repeated; merged checks appear in executedChecks. This keeps partial errors a subset of full errors (#381). Regression coverage pins case, NFC/NFD and NUL-bearing names for quick, XML-only and package-only selections under Word-valid and lenient (#423). A partial run can still pass when full extraction fails on a NUL-bearing name: omitted work can miss a defect.

    ValidateRunResult extends this with suffix (e.g. ".docx"), repairs (number of issues auto-repaired when autoRepair: true), and xsdWalk: { started, parts, eligible }. Validate.run() and jubarte.validate() return the shared ValidationResult, including metadata, without those extra fields.

    With autoRepair the run also reports repair outcomes for DOCX/DOCM and PPTX (#622). The plan appears in the path API's validate() result and in the CLI's --json output. The CLI's text mode lists error-severity issues only; the one other finding it prints is the auto-repair-staged-copy disclosure, on its own line. The byte APIs (new Validate().run(bytes), jubarte.validate(bytes)) have no autoRepair option, so neither surface carries the plan (#651). Non-info findings from before repair are grouped by path and code, then compared with the same group from that run's post-repair validation (#648).

    new Repair().run(bytes) and new Normalize().run(bytes) (jubarte.repair, jubarte.normalize) return bytes only for a package that packs. When unpack cannot extract the bytes, or the package still fails pack's validation, they reject with a PackageStepError: step is "unpack" or "pack", and issues holds the issues the validation failed on (#1157). pack's PackResult carries the same issues when it refuses. Each info-severity plan line gives the original count and says "Auto-repair cleared N; M remain": repair-plan means none remain, repair-plan-partial means some cleared and some remain, and repair-plan-unavailable means none cleared. Remaining findings carry "Fix manually: …" when guidance exists — one line lists every distinct guidance its survivors carry — or "No manual repair guidance is available." otherwise. Counts describe group outcomes, including indirect repairs; they do not identify individual occurrences or promise future repairs. New post-repair groups remain ordinary validation findings. No repairs are added.

    The paragraph-id repair stamps w14:paraId/w14:textId on the paragraphs and table rows that lack them. On each part it stamps, it also declares w14 on the part root and lists it in the root's mc:Ignorable, as Word writes it — reusing the prefix the root binds to the markup-compatibility namespace, else declaring mc — so the repaired part gains no mce-extension-not-ignorable finding. A root that binds w14 or mc to another namespace is left as it was. Word 16.115 opened the repaired output clean for a root with neither declaration, one listing w15 and one using a compat prefix, as it opened the earlier output with xmlns:w14 on each stamped element (Word probes session 40, s40a; #653).

    The durable-id repair gives each over-cap w16cid:durableId one new value and writes it into every w16cex:durableId that named the old one, so commentsExtensible.xml stays paired with commentsIds.xml. Before, each entry got its own random value and every extensible entry was left orphaned (#892). The two parts' spellings are matched as xsd:hexBinary values, whatever the case of their hex letters, so ffffffff in one part and FFFFFFFF in the other get the same new value (#904). The decimal durableIds in numbering.xml, which no part references, keep their per-element renumbering, and it still runs when the hex rewrite is refused.

    Validators (etc.) for the neurotic developer

    A place for "why isn't this more complete?" questions. If you came here because something looked suspiciously trim, this is where it gets explained.

    Why doesn't NS in lib/types.ts cover every namespace declared in the bundled XSDs?

    NS is a runtime lookup table for code that needs namespace URIs — getElementsByTagNameNSAll(root, NS.W, "p"), el.getAttributeNS(NS.W, "author"), the XPATH_NS prefix map. It is not a registry of every namespace that exists in OOXML.

    The bundled XSDs declare more namespace URIs than NS exposes. Schema-dispatch tables and compatibility-capability sets also describe namespaces used by the validators; NS remains a focused helper lookup. XSD validation is independent: the wasm engine reads the .xsd files directly, so NS membership has no effect on what gets validated.

    When a future validator needs c:chart (DrawingML chart) or v:shape (VML), add the constant to NS next to the validator that uses it — don't pre-populate speculatively. The schemas under src/scripts/office/schemas/ remain the source of truth for element definitions; NS is the source of truth for namespace URIs the TS code references at runtime.

    Releases and trusted publishing

    pnpm run release:check runs the prerelease preflight: type-check, type-aware lint, formatting, spelling, coverage tests, build, bundle inspection, and an npm pack dry run. It verifies that the package contains its ESM entry, declarations, and bundled Word schema. It publishes nothing.

    Update package.json and CHANGELOG.md, run the preflight, commit, and tag the tested commit. Create a GitHub release for that tag; mark versions such as 0.53.0-rc.1 as prereleases. Publishing uses npm trusted publishing from publish.yml, with the existing npm-publish environment, id-token: write, a GitHub-hosted Node 24 runner, and no dependency caches or npm publish token.

    The npm trusted publisher must authorize organization jandira-tech, repository docx-validate, workflow filename publish.yml, environment npm-publish, and direct npm publish. Package ownership and the trusted-publisher configuration are separate settings.

    The workflow checks out the exact release tag, verifies its package version and GitHub prerelease status, runs the preflight again, and publishes with provenance. Prerelease versions go to next; stable versions go to latest.

    To retry publishing an existing tag through the same GitHub workflow:

    pnpm run release:publish v0.53.0-rc.1

    This dispatches Actions; it does not use local npm credentials. Monitor the publish workflow for the registry result. An npm version already published cannot be overwritten.

    Desired Conversion Methodology

    Desired Conversion Methodology means fully parsing the original document into a semantic, format-independent representation — extracting its content and the meaning of that content (including its structure, formatting, and relationships, and every other discrete constituent component of the document (each, an "Element")), and not its byte form, such that the document can be faithfully reconstructed into any target format.

    Where an Element cannot be parsed semantically by available means — including, by default, DrawingML (<w:drawing>), VML pictures (<w:pict>), and embedded OLE objects (<w:object>) (each, a "Non-Parseable Element") — the Desired Conversion Methodology nonetheless applies in full to the entire document and to every Element enclosing that Non-Parseable Element; only the single, irreducible Element that resists semantic parsing may be preserved verbatim, and only after custom parsing techniques have been exhausted to reduce that residue to the smallest possible extent.

    For the avoidance of doubt, the Elements enumerated above are not the sole Non-Parseable Elements; every time an Element is classified as a Non-Parseable Element, such classification must (i) emit a warning during code execution (at runtime), and (ii) be documented in AGENTS.md, README.md and CLAUDE.md.
